## Lists — ordered, mutable sequences

A **list** is Python's workhorse container.
It holds an ordered sequence of any objects and supports in-place mutation.

```python
fruits = ['apple', 'banana', 'cherry']
fruits.append('date')        # add to end
fruits.insert(1, 'avocado')  # insert before index 1
fruits.remove('banana')      # remove first occurrence
print(fruits)                # ['apple', 'avocado', 'cherry', 'date']
```

### Common list methods

| Method | Description |
|--------|-------------|
| `append(x)` | Add `x` to the end |
| `insert(i, x)` | Insert `x` before index `i` |
| `remove(x)` | Remove first occurrence of `x` |
| `pop(i=-1)` | Remove and return item at index `i` |
| `sort(key=None, reverse=False)` | Sort in place |
| `reverse()` | Reverse in place |
| `index(x)` | Return index of first occurrence of `x` |
| `count(x)` | Count occurrences of `x` |

### Sorting: in place vs a new list, and stability

`list.sort()` sorts **in place and returns `None`**.
Pass a `key` function to sort by an arbitrary criterion.

```python
numbers = [5, 2, 8, 1, 9, 3]
numbers.sort()
print(numbers)  # [1, 2, 3, 5, 8, 9]

words = ['banana', 'apple', 'cherry']
words.sort(key=len)
print(words)    # ['apple', 'banana', 'cherry']
```

Use `sorted(iterable)` instead of `.sort()` when you need a new list and want to leave the original unchanged — `sorted()` always returns the list, `.sort()` never does. Chaining off `.sort()` (`x = lst.sort()`, or `lst.sort()[:3]`) is a real bug: `x`/the slice target is `None`.

Both `.sort()` and `sorted()` are **stable**: elements that compare equal under `key` keep their original relative order. This matters for multi-key sorting — sort by the least significant key first, then by the most significant:

```python
people = [('carol', 30), ('alice', 30), ('dave', 25), ('bob', 25)]
people.sort(key=lambda p: p[1])
print(people)  # [('dave', 25), ('bob', 25), ('carol', 30), ('alice', 30)]
```

Stability alone only guarantees the *original* order survives within an age group — it does not alphabetize the names. For a true multi-key sort, put every key in one tuple:

```python
people.sort(key=lambda p: (p[1], p[0]))
print(people)  # [('bob', 25), ('dave', 25), ('alice', 30), ('carol', 30)]
```

## Aliasing: assignment never copies

`b = a` does **not** create a second list — it binds a second name to the *same* object. Mutating through either name is visible through both:

```python
a = [1, 2, 3]
b = a
b.append(4)
print(a)  # [1, 2, 3, 4] — a changed too, even though only b was touched
```

`a[:]` (or `list(a)`, or `a.copy()`) makes a **shallow copy**: a new outer list, but every element is the *same object* it was before. If the elements are themselves mutable, they are still shared:

```python
a = [1, [2, 3]]
c = a[:]
c[1].append(9)
print(a)  # [1, [2, 3, 9]] — the inner list is shared, so a saw the mutation too
```

Only `copy.deepcopy()` recursively duplicates nested mutable structure so nothing is shared:

```python
import copy
a = [1, [2, 3]]
d = copy.deepcopy(a)
d[1].append(100)
print(a)  # [1, [2, 3]] — untouched; d's inner list is an independent object
```

### The `[[0] * n] * m` trap

`[[0] * 3] * 3` multiplies a *list object*, not the values inside it — every row of the resulting grid is the same inner list, aliased three times:

```python
grid = [[0] * 3] * 3
grid[0][0] = 1
print(grid)  # [[1, 0, 0], [1, 0, 0], [1, 0, 0]] — every row "changed"
```

The fix is a comprehension, which evaluates `[0] * 3` freshly on every iteration:

```python
grid = [[0] * 3 for _ in range(3)]
grid[0][0] = 1
print(grid)  # [[1, 0, 0], [0, 0, 0], [0, 0, 0]]
```

## In-place mutation vs rebinding: `+=` on a list vs a tuple

`+=` looks like one operator, but it does something different depending on the type on the left. On a list, `+=` calls `__iadd__`, which extends the list **in place** — every alias sees the change. On a tuple, there is no in-place `__iadd__`; Python falls back to `t = t + (...)`, which builds a brand-new tuple and **rebinds the name** — aliases still point at the old tuple:

```python
la = [1, 2]
lb = la
la += [3]
print(la, lb)  # [1, 2, 3] [1, 2, 3] — same object, both names see it

ta = (1, 2)
tb = ta
ta += (3,)
print(ta, tb)  # (1, 2, 3) (1, 2) — ta now points at a new tuple; tb is unaffected
```

## Membership testing: `in` on a list vs a set

`x in some_list` checks elements one at a time — `O(n)` in the size of the list. `x in some_set` hashes `x` and looks up a bucket — `O(1)` on average, regardless of how large the set is. Both give the same boolean answer; only the cost differs, and it only shows up as the collection grows:

```python
names_list = ['alice', 'bob', 'carol']
names_set = {'alice', 'bob', 'carol'}
print('bob' in names_list, 'bob' in names_set)  # True True — same answer, different cost
```

If a function does repeated `in` checks against a list that could grow large, converting it to a `set` (or `frozenset`, if it must not change) is a one-line performance fix.

## Tuples — ordered, immutable sequences

A **tuple** is like a list but cannot be modified after creation.
Use tuples to represent fixed records where position carries meaning.

```python
rgb = (255, 128, 0)   # an orange colour
point = (3.0, 4.0)    # a 2-D coordinate
row = (1, 'Alice', 42)  # a database row
```

"Immutable" only means a tuple's own slots can't be reassigned — it says nothing about whether an *element* inside the tuple is itself mutable:

```python
t = (1, [2, 3])
t[0] = 99          # TypeError: 'tuple' object does not support item assignment
```

```python
t[1].append(4)     # allowed — the list inside the tuple can still change
print(t)            # (1, [2, 3, 4])
```

That mutable element also has a consequence for hashing: a tuple is only hashable — and only usable as a dict key or set member — if *every* element it contains is hashable.

```python
d = {t: 'value'}   # TypeError: cannot use 'tuple' as a dict key (unhashable type: 'list')
```

A tuple of only hashable elements works fine as a key:

```python
point = (1, 2)
by_point = {point: 'ok'}
```

### Tuple unpacking

Python lets you unpack a tuple (or any iterable) directly into variables.
The number of variables must match the length — unless you use `*` to capture the rest.

```python
coords = (10.5, 20.3, 30.1)
x, y, z = coords
print(x, y, z)           # 10.5 20.3 30.1

first, *rest = [1, 2, 3, 4, 5]
print(first)             # 1
print(rest)              # [2, 3, 4, 5]
```

### Accessing tuple fields by index — or by name

Without a name, tuple fields are accessed by integer index.
Assign constants for readability:

```python
RGB = (255, 128, 0)
RED   = 0
GREEN = 1
BLUE  = 2

print(RGB[RED])    # 255
print(RGB[GREEN])  # 128
print(RGB[BLUE])   # 0
```

`typing.NamedTuple` gives the same tuple (index access, unpacking, equality, hashability) plus named attribute access, in about three lines. A `@dataclass` looks similar but is a different kind of object — mutable by default, and not usable as a dict key unless you opt in:

```python
from typing import NamedTuple
from dataclasses import dataclass

class PointNT(NamedTuple):
    x: int
    y: int

@dataclass
class PointDC:
    x: int
    y: int
```

```python
pnt = PointNT(1, 2)
pnt.x = 99  # AttributeError: can't set attribute — still a tuple, still immutable
```

```python
pdc = PointDC(1, 2)
pdc.x = 99  # allowed — a dataclass instance is a plain, mutable object
```

Reach for `NamedTuple` when the value is a small, fixed, hashable record (safe as a dict key, safe to pass around without worrying who mutates it). Reach for `@dataclass` when you want a mutable object with class-like behavior (methods, inheritance, `field(default_factory=...)`).

## Beyond list: `deque` for both ends

A `list`'s `insert(0, x)` and `pop(0)` are `O(n)` — every other element has to shift. `collections.deque` is a double-ended queue with `O(1)` append and pop at **both** ends, at the cost of `O(n)` random access by index (no slicing):

```python
from collections import deque
dq = deque([1, 2, 3])
dq.appendleft(0)
dq.append(4)
print(dq)  # deque([0, 1, 2, 3, 4])
```

Use `deque` for queues, sliding windows, and undo/history buffers; keep `list` when you mostly index, slice, or append at the end only.

## Trade-offs

| What you get | Benefit | Cost |
|---|---|---|
| `list` (mutable) | append/sort/mutate in place, no copying to change it | every alias shares the mutation — easy to change something you didn't mean to |
| `tuple` (immutable) | safe to hash, share, and use as a dict key or set member | fixed size and order; "immutable" only protects the tuple's own slots, not a mutable element inside it |
| `list.sort()` (in place) | no new list allocated | returns `None` — chaining off it (`.sort()[:3]`) is a `TypeError` |
| `sorted()` (new list) | original is untouched, safe to chain | always allocates a new list, even for a quick peek |
| `deque` | `O(1)` append/pop at both ends | `O(n)` random access by index, no slicing |

## Common Misconceptions

- **"`b = a` copies the list"** — fact: it binds a second name to the same object; mutating through `b` also changes what `a` sees.
- **"`a[:]` makes a fully independent copy"** — fact: `a[:]` is a shallow copy — nested mutable elements (like an inner list) are still shared.
- **"`list.sort()` returns the sorted list"** — fact: `.sort()` always returns `None`; only `sorted()` returns a new list.
- **"A tuple is always safe as a dict key"** — fact: only if every element inside it is hashable — a tuple holding a list raises `TypeError: unhashable type: 'list'`.
- **"`+=` behaves the same on a list and a tuple"** — fact: on a list it mutates in place (aliases see it); on a tuple it rebuilds a new tuple and rebinds the name (aliases do not see it).

## Reading AI-generated code

- Does a function that receives a list mutate it in place *and* `return` it? Check every call site for whether the caller expects the original list to survive untouched.
- Does the code chain directly off `.sort()` (`.sort()[:3]`, `x = lst.sort()`)? `.sort()` always returns `None` — that line is a bug.
- Is a 2D grid built with `[[default] * cols] * rows`? Every row is the *same* list object — look for the comprehension form (`[[default] * cols for _ in range(rows)]`) instead.
- Does `+=` appear on something that might be a tuple, in code that assumes the original object was mutated in place? Tuples rebind instead of mutating.
- Is a tuple used as a dict key or set element without checking that every element inside it is itself hashable?

<Callout title="Tuples are immutable — but only at the top level">
A tuple's own slots can never be reassigned, and `my_tuple[0] = 99` always raises `TypeError: 'tuple' object does not support item assignment`.
That immutability makes a tuple hashable — safe as a dictionary key or set member — **only if every element inside it is also hashable**. A tuple holding a list is not hashable, because the list inside it can still change.
Use tuples for fixed records made entirely of immutable data; reach for `NamedTuple` when you also want named fields.
