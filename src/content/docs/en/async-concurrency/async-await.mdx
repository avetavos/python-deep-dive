## Sequential vs concurrent awaiting

The key insight in async programming is the difference between awaiting coroutines **sequentially**
and scheduling them to run **concurrently**.

Awaiting one coroutine at a time is sequential — each coroutine must finish before the next starts:

```python
import asyncio

async def fetch(label: str, delay: float) -> str:
    await asyncio.sleep(delay)
    return f"{label} result"

async def sequential() -> None:
    a = await fetch("A", 0.3)   # waits 0.3 s
    b = await fetch("B", 0.2)   # waits 0.2 s after A finishes
    print(a, b)
    # Total: ~0.5 s

asyncio.run(sequential())
```

Using `asyncio.gather` runs them concurrently — total time equals the slowest, not the sum:

```python
import asyncio

async def fetch(label: str, delay: float) -> str:
    await asyncio.sleep(delay)
    return f"{label} result"

async def concurrent() -> None:
    a, b = await asyncio.gather(
        fetch("A", 0.3),
        fetch("B", 0.2),
    )
    print(a, b)
    # Total: ~0.3 s

asyncio.run(concurrent())
```

## `asyncio.create_task` — explicit task scheduling

`asyncio.create_task(coro)` wraps a coroutine in a `Task` and immediately schedules it on the
running event loop. Unlike calling a coroutine directly, the task starts running as soon as the
current coroutine yields control.

```python
import asyncio

async def worker(name: str, delay: float) -> str:
    print(f"{name}: starting")
    await asyncio.sleep(delay)
    print(f"{name}: done")
    return f"{name}-result"

async def main() -> None:
    # Schedule both tasks immediately — they run concurrently
    task_a = asyncio.create_task(worker("A", 0.3))
    task_b = asyncio.create_task(worker("B", 0.1))

    # Await them to collect results
    result_a = await task_a
    result_b = await task_b
    print(result_a, result_b)

asyncio.run(main())
# A: starting
# B: starting
# B: done
# A: done
# A-result B-result
```

Observe that "B: done" appears before "A: done" even though we `await task_a` first —
the tasks run concurrently and B finishes sooner.

## The fire-and-forget trap: keep a reference to your tasks

Calling `asyncio.create_task(coro)` without storing the result compiles and often even runs fine in
a small demo — which is exactly what makes it dangerous. The official docs are explicit about the
risk: *"the event loop only keeps weak references to tasks. A task that isn't referenced elsewhere
may get garbage collected at any time, even before it's done."* Nothing in the language forces you
to keep a reference, so nothing warns you when you forget:

```python
import asyncio

async def background_job(label: str) -> None:
    await asyncio.sleep(0.05)
    print(f"{label}: finished")

async def fire_and_forget() -> None:
    asyncio.create_task(background_job("leaked"))   # no variable holds the Task
    await asyncio.sleep(0.1)   # only works because the loop's own scheduling keeps it alive here
```

The fix costs nothing and has no downside — keep the task in a set, and let a done-callback clean the
set up when it finishes:

```python
import asyncio

background_tasks: set[asyncio.Task] = set()

async def background_job(label: str) -> None:
    await asyncio.sleep(0.05)
    print(f"{label}: finished")

def spawn(coro) -> asyncio.Task:
    task = asyncio.create_task(coro)
    background_tasks.add(task)
    task.add_done_callback(background_tasks.discard)
    return task
```

Or, if the fire-and-forget tasks share a lifetime with a block of code, prefer `TaskGroup` over
manual bookkeeping entirely — it makes "wait for everything I started" the default instead of
something you have to remember.

## `TaskGroup` cancellation vs `gather(return_exceptions=True)`

Both `TaskGroup` and `gather(return_exceptions=True)` let you run several coroutines and see every
result even if some fail — but they disagree about what happens to the *survivors*:

```python
import asyncio

async def worker(label: str, delay: float, fail: bool) -> str:
    await asyncio.sleep(delay)
    if fail:
        raise ValueError(f"{label} failed")
    return f"{label} ok"

async def main() -> None:
    results = await asyncio.gather(
        worker("A", 0.05, False),
        worker("B", 0.02, True),
        worker("C", 0.08, False),
        return_exceptions=True,
    )
    print(results)
    # ['A ok', ValueError('B failed'), 'C ok'] — C still ran to completion

asyncio.run(main())
```

```python
import asyncio

async def worker(label: str, delay: float, fail: bool) -> str:
    await asyncio.sleep(delay)
    if fail:
        raise ValueError(f"{label} failed")
    return f"{label} ok"

async def main() -> None:
    try:
        async with asyncio.TaskGroup() as tg:
            tg.create_task(worker("A", 0.05, False))
            tg.create_task(worker("B", 0.02, True))
            tg.create_task(worker("C", 0.08, False))
    except* ValueError as eg:
        print([str(e) for e in eg.exceptions])
        # ['B failed'] — B's failure cancelled C before its 0.08s sleep finished

asyncio.run(main())
```

`gather(return_exceptions=True)` never cancels anything — every coroutine you passed in runs to
completion regardless of the others' outcomes, and you sort out successes from exceptions yourself.
`TaskGroup` treats one failure as a reason to cancel the whole group: it is the right default when
the tasks are working toward one goal together (a request fan-out where a partial result is
useless), and the wrong one when you genuinely want every result independent of the others'
failures (a batch job reporting per-item status).

## Timeouts: `asyncio.timeout()` and `wait_for`

`asyncio.timeout()` (3.11+) is a context manager: everything inside is cancelled if the block does
not finish within the given number of seconds, raising `TimeoutError`.

```python
import asyncio

async def slow_op() -> str:
    await asyncio.sleep(5)
    return "done"

async def main() -> None:
    try:
        async with asyncio.timeout(0.1):
            await slow_op()
    except TimeoutError:
        print("operation timed out")

asyncio.run(main())
# operation timed out
```

`asyncio.wait_for(coro, timeout)` is the older, coroutine-shaped equivalent — it wraps a single
awaitable instead of a block, which matters if you need to bound several statements at once (only
`timeout()` can wrap more than one line). Both cancel the same way and both raise `TimeoutError`
(as of 3.11, `asyncio.TimeoutError` is an alias for the builtin). `asyncio.shield(coro)` is the
opposite tool: it protects an awaitable from being cancelled *by its caller* — useful when a cleanup
step must finish even if the surrounding operation is cancelled — but it does not protect against a
`timeout()`/`wait_for` that wraps the shielded call itself timing out; the coroutine inside a
`shield` can still be cancelled independently.

## Blocking calls freeze the loop — `time.sleep` vs `asyncio.sleep`

`time.sleep()` blocks the entire OS thread the event loop runs on. Called from inside a coroutine,
it does not "pause that task" the way `asyncio.sleep()` does — it stops *everything*, because there
is only one thread running the loop:

```python
import asyncio

async def heartbeat(n: int) -> None:
    for i in range(n):
        await asyncio.sleep(0.03)
        print(f"heartbeat {i}")

def blocking_sleep(seconds: float) -> str:
    import time
    time.sleep(seconds)      # blocks the WHOLE event loop thread
    return "worker done"

async def main() -> None:
    hb = asyncio.create_task(heartbeat(2))
    result = await asyncio.to_thread(blocking_sleep, 0.08)  # runs off the event loop's thread
    print(result)
    await hb

asyncio.run(main())
# heartbeat 0
# heartbeat 1
# worker done
```

`asyncio.to_thread(fn, *args)` (3.9+) is the fix: it runs a genuinely blocking call — `time.sleep`,
a synchronous DB driver, CPU-light file I/O — in a thread pool, so the event loop keeps serving
other coroutines while it waits. It is a thin wrapper over
`loop.run_in_executor(None, functools.partial(fn, *args))`, covered in the GIL & Threads lesson.

## `Semaphore` — bounding concurrency

`asyncio.Semaphore(n)` lets at most `n` coroutines hold it at once — the standard way to cap
concurrent requests to a rate-limited API or a connection pool:

```python
import asyncio

async def limited_call(sem: asyncio.Semaphore, label: str, active: list) -> None:
    async with sem:
        active.append(label)
        print(f"{label}: running, concurrent={len(active)}")
        await asyncio.sleep(0.05)
        active.remove(label)

async def main() -> None:
    sem = asyncio.Semaphore(2)
    active: list = []
    await asyncio.gather(*[limited_call(sem, f"job-{i}", active) for i in range(4)])

asyncio.run(main())
# never more than 2 "running" lines are concurrent
```

## `Queue` — producer/consumer

`asyncio.Queue` is the async-native equivalent of `queue.Queue`: `put`/`get` are coroutines, so a
full queue suspends the producer (instead of blocking a thread) until the consumer drains it.

```python
import asyncio

async def producer(q: asyncio.Queue, n: int) -> None:
    for i in range(n):
        await q.put(i)
    await q.put(None)   # sentinel signals "no more items"

async def consumer(q: asyncio.Queue, out: list) -> None:
    while True:
        item = await q.get()
        if item is None:
            break
        out.append(item)

async def main() -> None:
    q: asyncio.Queue = asyncio.Queue(maxsize=2)   # bounded — producer waits if it fills up
    out: list = []
    await asyncio.gather(producer(q, 4), consumer(q, out))
    print(out)   # [0, 1, 2, 3]

asyncio.run(main())
```

## `Lock` — check-then-act is still a race across an `await`

A single-threaded event loop means no two coroutines run Python bytecode at the same *instant* — but
that does **not** mean shared state is safe. Any `await` between a check and the action it guards is
a window where another coroutine can run and change that state first:

```python
import asyncio

class Account:
    def __init__(self, balance: int) -> None:
        self.balance = balance

async def withdraw_unsafe(acct: Account, amount: int) -> None:
    if acct.balance >= amount:   # check
        await asyncio.sleep(0)   # <-- another coroutine can run right here
        acct.balance -= amount   # act -- based on a now-stale read

async def main() -> None:
    acct = Account(balance=100)
    await asyncio.gather(withdraw_unsafe(acct, 80), withdraw_unsafe(acct, 80))
    print(acct.balance)   # -60 -- both checks passed before either write happened

asyncio.run(main())
```

`asyncio.Lock` closes the window by serializing the check-and-act as one unit:

```python
import asyncio

class Account:
    def __init__(self, balance: int) -> None:
        self.balance = balance
        self.lock = asyncio.Lock()

async def withdraw_safe(acct: Account, amount: int) -> None:
    async with acct.lock:
        if acct.balance >= amount:
            await asyncio.sleep(0)
            acct.balance -= amount

async def main() -> None:
    acct = Account(balance=100)
    await asyncio.gather(withdraw_safe(acct, 80), withdraw_safe(acct, 80))
    print(acct.balance)   # 20 -- the second withdrawal correctly sees the updated balance

asyncio.run(main())
```

This is the async-world version of a truth that also holds for threads: **no data races (undefined
behavior) does not mean no race conditions.** A single-threaded event loop guarantees you will never
corrupt memory from two coroutines writing at once — but it makes zero guarantees about the *logical*
correctness of a check-then-act sequence that spans an `await`. `asyncio.Event` is the matching
primitive for the opposite direction — not "only one at a time," but "everyone wait until I say go":
`await event.wait()` suspends until another coroutine calls `event.set()`.

## Practical patterns: retry, rate limiting, and graceful shutdown

**Retry with exponential backoff and jitter** — retrying immediately after a transient failure
often just repeats the failure (or hits a server that is already overloaded); backoff spaces
retries out, and jitter (randomizing the delay) prevents many clients from retrying in lockstep:

```python
import asyncio
import random

class FlakyError(Exception):
    pass

async def retry_with_backoff(coro_fn, *, max_attempts: int = 5, base: float = 0.01) -> object:
    for attempt in range(1, max_attempts + 1):
        try:
            return await coro_fn()
        except FlakyError:
            if attempt == max_attempts:
                raise
            delay = base * (2 ** (attempt - 1)) + random.uniform(0, base)
            await asyncio.sleep(delay)
```

**Rate limiting** — a token bucket caps how often an action may happen, independent of how many
callers are waiting:

```python
import asyncio

class RateLimiter:
    def __init__(self, rate: int, period: float) -> None:
        self.rate = rate
        self.period = period
        self.tokens = float(rate)

    async def acquire(self) -> None:
        while self.tokens < 1:
            await asyncio.sleep(self.period / self.rate)
            self.tokens += 1
        self.tokens -= 1
```

**Graceful shutdown** — a long-running service should stop accepting new work and let in-flight
work finish (or cancel it deliberately) when asked to stop, rather than being killed mid-request. The
usual shape is a shutdown `asyncio.Event` set from a signal handler, with worker loops checking it:

```python
import asyncio
import signal

async def worker(shutdown: asyncio.Event) -> None:
    while not shutdown.is_set():
        await asyncio.sleep(0.1)   # do one unit of work per iteration in a real service
    print("worker exiting cleanly")

async def main() -> None:
    shutdown = asyncio.Event()
    loop = asyncio.get_running_loop()
    loop.add_signal_handler(signal.SIGTERM, shutdown.set)   # Unix only; not testable on Pyodide
    async with asyncio.TaskGroup() as tg:
        tg.create_task(worker(shutdown))
        # ... other tasks ...
```

`loop.add_signal_handler` is Unix-only and needs a real OS signal to demonstrate, so it is not part
of the runnable demo below — the pattern (an `Event`, workers polling it, a `TaskGroup` so shutdown
waits for every worker) is identical whether the trigger is a signal or, as in the demo, another
coroutine calling `shutdown.set()`.

### Structured concurrency

`TaskGroup`'s core thesis — every task you spawn has a clear owner, and that owner cannot exit
until all its children have finished or been cancelled — is called **structured concurrency**. It
rules out an entire class of bugs that `create_task`-and-forget code invites: a task outliving the
scope that logically owns it, an exception in a child that nobody ever observes, a program exiting
while background work is still in flight. `gather` and bare `create_task` do not enforce this;
`TaskGroup` does.

### Beyond the standard library

`asyncio` is CPython's only built-in async framework, but two third-party libraries are worth
knowing about even though they cannot run in this course's Pyodide sandbox: **anyio** provides a
single API that runs on top of either `asyncio` or `trio`'s event loop, useful for library code that
should not force a choice on its caller; **trio** pioneered the structured-concurrency model that
`TaskGroup` later brought into `asyncio` itself. For HTTP specifically, `httpx.AsyncClient` is the
async-native counterpart to `requests` — a synchronous `requests.get()` call inside a coroutine
blocks the loop exactly like `time.sleep` above.

## Nested `asyncio.run` raises `RuntimeError`

Calling `asyncio.run` twice, one after the other, at the top level is fine (see the asyncio Basics
lesson). Calling it **from inside** a coroutine that is already running on a loop is not — there is
already a loop running in this thread, and `asyncio.run` refuses to start a second one:

```python
import asyncio

async def inner() -> None:
    print("inner")

async def main() -> None:
    asyncio.run(inner())   # calling asyncio.run() from inside a running event loop

try:
    asyncio.run(main())
except RuntimeError as e:
    print(f"RuntimeError: {e}")
    # RuntimeError: asyncio.run() cannot be called from a running event loop
```

This is also the classic Jupyter-notebook surprise: a notebook cell already runs inside an event
loop, so a top-level `asyncio.run(...)` in a cell raises the same error — `await` the coroutine
directly instead.

<Callout title="This example is verified on CPython only">
Run locally, `asyncio.run(inner())` above reliably raises `RuntimeError: asyncio.run() cannot be
called from a running event loop` on `python3.14`. Testing the same code in this course's Pyodide
sandbox showed no such error — Pyodide's event loop integration does not reject the nested call the
same way CPython's does. Because the two runtimes disagree here, this example is intentionally left
out of the Depth demo Playground below; treat it as a CPython-verified fact, not a browser-verified
one.

## Mental Model

Think of `TaskGroup` as a project manager who will not go home until every task they assigned is
either done or explicitly cancelled — and who cancels the rest of the team the moment one task
fails, because continuing toward a goal that is already broken wastes everyone's time. `gather` is
a manager with no such instinct: they collect whatever each worker produces, success or failure,
and leave the sorting to you. Neither manager makes the workers themselves safe from each other —
that is still the job of a `Lock`, `Semaphore`, or `Queue` you add yourself.

## Trade-offs

| What you get | Benefit | Cost |
|---|---|---|
| `create_task` (bare) | Fire off work immediately, minimal ceremony | Nothing enforces you keep a reference — silently collectible |
| `TaskGroup` | Structured lifetime, one failure cancels the rest | All-or-nothing; a batch that wants partial success needs `gather` instead |
| `gather(return_exceptions=True)` | Every task runs to completion regardless of others' failures | You must inspect each result for `isinstance(r, Exception)` yourself |
| `Semaphore` / rate limiting | Protects a downstream service or pool from overload | Adds latency to callers once the limit is hit |
| `asyncio.to_thread` | Blocking calls stop freezing the loop | Thread-pool overhead; still subject to the GIL for pure-Python work |
| Retry with backoff + jitter | Survives transient failures without hammering a struggling server | Masks a permanently broken dependency for `max_attempts` tries first |

## Common Misconceptions

- **"`create_task` and `await coro` are interchangeable."** `create_task` schedules immediately and
  returns control right away; a bare `await coro` runs (and blocks on) that one coroutine before
  moving on. Mixing them up is exactly how a "concurrent" fan-out silently becomes sequential.
- **"A task with no variable pointing at it is definitely garbage collected."** Usually the loop's
  own internal scheduling keeps it alive long enough to finish in a short-lived demo — which is what
  makes this bug so easy to miss in code review and so unreliable to reproduce on demand. The
  official recommendation to keep a reference exists regardless of whether any particular run shows
  a problem.
- **"`gather(return_exceptions=True)` and `TaskGroup` are just two spellings of the same thing."**
  They differ on purpose: `gather` never cancels a sibling; `TaskGroup` always does on first failure.
- **"A single-threaded event loop means shared state never needs a lock."** No two coroutines run
  bytecode at the same instant, but a check-then-act sequence spanning an `await` is still a race —
  the check can be stale by the time the action runs.
- **"`asyncio.shield` makes a coroutine uncancellable."** It only protects against cancellation
  *propagating in from the caller's cancellation*; the shielded coroutine can still be cancelled on
  its own, and a `timeout()`/`wait_for` wrapping the shield still applies.

## Reading AI-generated code

Before trusting generated task/concurrency code, check for these:

- Does every `asyncio.create_task(...)` call assign its result to something that outlives the
  current statement (a variable, a set, a `TaskGroup`)? A bare `asyncio.create_task(coro())` on its
  own line is a fire-and-forget task with nothing tracking it.
- Is `gather` used where the tasks are actually working toward one shared goal (should one failure
  cancel the rest — i.e., should this really be a `TaskGroup`)?
- Does a shared object get read, then mutated, with an `await` in between, and no `Lock` around the
  whole sequence?
- Is a genuinely blocking call (`time.sleep`, a synchronous `requests.get`, heavy CPU work) sitting
  directly inside an `async def` instead of behind `asyncio.to_thread` or `run_in_executor`?
- Does a retry loop retry forever with no `max_attempts`, or retry with a fixed delay that could
  synchronize many clients into hammering a struggling server at the same instant (no jitter)?

schedule every fetch first and wait on all of them together:
`results = await asyncio.gather(*[fetch(session, u) for u in urls])`, or a `TaskGroup` if a failed

<Callout title="Scheduling vs waiting are two different actions">
`create_task`/`TaskGroup.create_task` *schedule* a coroutine to start running now. `await` *waits*
for something to finish. A `for` loop full of `await` calls only ever does the second thing, one at
a time — concurrency requires the first thing to happen for more than one coroutine before you wait
on any of them.
</Callout>
