## The event loop

`asyncio` runs on an **event loop**: a scheduler that keeps a queue of coroutines and callbacks,
executes them one at a time, and switches between them whenever one suspends at an `await` expression.

No OS threads are created. The concurrency is **cooperative** — a coroutine must voluntarily yield
control with `await` for other coroutines to progress.

```python
import asyncio

async def say(message: str, delay: float) -> None:
    await asyncio.sleep(delay)
    print(message)

async def main() -> None:
    await say("Hello", 0.1)
    await say("World", 0.1)

asyncio.run(main())
# Hello
# World
```

In this sequential example, `say("World", …)` does not start until `say("Hello", …)` finishes.

## `async def` and coroutines

A function defined with `async def` is a **coroutine function**. Calling it does not execute the body
— it returns a **coroutine object**. The body only runs when the coroutine is awaited or scheduled
on the event loop.

```python
import asyncio

async def greet(name: str) -> str:
    return f"Hello, {name}!"

# Calling greet() returns a coroutine object — nothing runs yet
coro = greet("Python")
print(type(coro))          # <class 'coroutine'>

# Never awaiting it is a real bug. Under `python3.14 -X dev`, deleting the
# never-awaited coroutine triggers:
#   RuntimeWarning: coroutine 'greet' was never awaited
del coro

# Fix: await it to actually run the body
result = asyncio.run(greet("Python"))
print(result)              # Hello, Python!

# If you decide not to run a coroutine after all, close it explicitly —
# closing (instead of just dropping the reference) silences the warning
unused = greet("Python")
unused.close()
```

## The never-awaited warning is not cosmetic

The `RuntimeWarning` above is CPython telling you a coroutine's body **never ran at all** — not a
lint nitpick. In production code this usually means a forgotten `await` in front of a call, which
silently turns an intended network request, database write, or `asyncio.sleep` into a no-op:

```python
async def send_email(to: str) -> None:
    print(f"sending email to {to}")

async def process_signup(email: str) -> None:
    send_email(email)   # BUG: missing `await` — the coroutine object is created and discarded
    print("signup processed")
```

Calling `process_signup("a@example.com")` prints `signup processed` and returns normally — no
exception, no email sent, no obvious symptom. The only real-time signal is the `RuntimeWarning` once
the coroutine object is garbage-collected, which is why `-X dev` (or `-W error::RuntimeWarning` in
CI) belongs in every asyncio test suite: it turns a silent no-op into a hard failure at the exact
call site that forgot `await`.

## `await` suspends and resumes

The `await` keyword can only appear inside an `async def` function.
It suspends the current coroutine and yields control back to the event loop.
The event loop runs other ready coroutines and returns to this one when the awaited object completes.

```python
import asyncio

async def fetch_data(label: str) -> str:
    print(f"  {label}: starting fetch")
    await asyncio.sleep(0.05)          # suspends here
    print(f"  {label}: fetch done")
    return f"data-{label}"

async def main() -> None:
    result = await fetch_data("A")
    print(result)

asyncio.run(main())
#   A: starting fetch
#   A: fetch done
# data-A
```

## Sequential `await` in a loop vs `asyncio.gather`

Writing `for item in items: await do(item)` is the single most common way generated async code
looks concurrent but is not. Each iteration fully waits for the previous one — the loop is
sequential, one `await` at a time:

```python
import asyncio
import time

async def fetch(label: str) -> str:
    await asyncio.sleep(0.2)
    return f"{label} done"

async def sequential() -> None:
    start = time.perf_counter()
    results = []
    for label in ["A", "B", "C"]:
        results.append(await fetch(label))   # each await blocks the loop until this one finishes
    print(f"sequential: {round(time.perf_counter() - start, 1)}s")   # ~0.6s (3 × 0.2s)

asyncio.run(sequential())
```

`asyncio.gather` schedules all three coroutines up front instead, so the total time is the *slowest
one*, not the sum:

```python
import asyncio
import time

async def fetch(label: str) -> str:
    await asyncio.sleep(0.2)
    return f"{label} done"

async def concurrent() -> None:
    start = time.perf_counter()
    await asyncio.gather(fetch("A"), fetch("B"), fetch("C"))
    print(f"gather: {round(time.perf_counter() - start, 1)}s")   # ~0.2s (all three overlap)

asyncio.run(concurrent())
```

The rule of thumb: a `for` loop of independent `await` calls is a bug waiting to be found in code
review, unless the iterations genuinely must run in order (each one depends on the previous result).

## `asyncio.run` — entry point

`asyncio.run(coro)` creates a new event loop, runs the coroutine to completion, closes the loop,
and returns the result. It is the standard entry point for async programs.

```python
import asyncio

async def compute(x: int) -> int:
    await asyncio.sleep(0)     # yield to event loop once
    return x ** 2

result = asyncio.run(compute(7))
print(result)    # 49
```

Calling `asyncio.run` a second time, sequentially, after the first call has already returned and
closed its loop is fine — each call gets its own fresh loop:

```python
import asyncio

async def compute(x: int) -> int:
    await asyncio.sleep(0)
    return x ** 2

print(asyncio.run(compute(3)))   # 9
print(asyncio.run(compute(3)))   # 9 — a second, independent event loop, same process
```

What is *not* fine is calling `asyncio.run` **from inside** a coroutine that is already running on
a loop — that is nesting, not sequencing, and it raises `RuntimeError`. See the Async / Await lesson
for that failure mode.

## `asyncio.gather` — running coroutines concurrently

`asyncio.gather(*coroutines)` schedules all coroutines concurrently and awaits all of them.
Results are returned in the same order as the input coroutines.

```python
import asyncio

async def step(label: str, delay: float) -> str:
    await asyncio.sleep(delay)
    return f"{label} done"

async def main() -> None:
    results = await asyncio.gather(
        step("A", 0.3),
        step("B", 0.1),
        step("C", 0.2),
    )
    print(results)
    # ['A done', 'B done', 'C done']   — always input order
    # Total time ≈ 0.3 s, not 0.6 s

asyncio.run(main())
```

Results are always in **input order**, regardless of completion order.
This mirrors JavaScript's `Promise.all`.

## Handling failures with `return_exceptions=True`

By default, if any coroutine raises, `gather` propagates the first exception and cancels the rest.
Pass `return_exceptions=True` to collect exceptions as values instead (like `Promise.allSettled`).

```python
import asyncio

async def risky(n: int) -> int:
    if n == 2:
        raise ValueError(f"n={n} is bad")
    return n * 10

async def main() -> None:
    results = await asyncio.gather(
        risky(1),
        risky(2),
        risky(3),
        return_exceptions=True,
    )
    for r in results:
        if isinstance(r, Exception):
            print(f"Error: {r}")
        else:
            print(f"OK: {r}")

asyncio.run(main())
# OK: 10
# Error: n=2 is bad
# OK: 30
```

## Python 3.11+: `asyncio.TaskGroup`

`asyncio.TaskGroup` (3.11+) is the structured-concurrency alternative to `gather`.
If any task raises, the group cancels all remaining tasks automatically.

```python
import asyncio

async def work(label: str, delay: float) -> str:
    await asyncio.sleep(delay)
    return f"{label} complete"

async def main() -> None:
    async with asyncio.TaskGroup() as tg:
        task_a = tg.create_task(work("A", 0.2))
        task_b = tg.create_task(work("B", 0.1))
    # Both tasks are done here; exceptions are re-raised automatically
    print(task_a.result())
    print(task_b.result())

asyncio.run(main())
```

## `async with` and `async for`

Asynchronous context managers and iterators exist for the same reason their synchronous counterparts
do — setup/teardown and iteration — except `__aenter__`/`__aexit__`/`__anext__` are coroutines, so
each step can itself `await` (an async DB driver flushing a connection, an async generator waiting
on the next chunk):

```python
import asyncio

class AsyncResource:
    async def __aenter__(self) -> "AsyncResource":
        await asyncio.sleep(0.01)          # e.g. an async connection handshake
        print("acquired resource")
        return self

    async def __aexit__(self, exc_type, exc, tb) -> None:
        await asyncio.sleep(0.01)          # e.g. an async flush/close
        print("released resource")

async def numbers(n: int):
    for i in range(n):
        await asyncio.sleep(0.01)
        yield i                             # an async generator — defines __anext__ automatically

async def main() -> None:
    async with AsyncResource() as res:
        print("using the resource")

    async for i in numbers(3):
        print(f"got {i}")

asyncio.run(main())
```

Breaking out of an `async for` loop early over an async generator can leave it suspended mid-`yield`
without running its cleanup (`finally`, `try`/`except GeneratorExit`). `contextlib.aclosing` closes
it deterministically either way, mirroring what a plain `for`/generator combination gets for free
from reference counting:

```python
from contextlib import aclosing

async def numbers(n: int):
    for i in range(n):
        yield i

async def main() -> None:
    async with aclosing(numbers(5)) as gen:
        async for i in gen:
            if i == 1:
                break
    # gen.aclose() already ran here, even though the loop exited early

asyncio.run(main())
```

## `CancelledError` is a `BaseException` — always re-raise it

`asyncio.CancelledError` inherits from `BaseException`, not `Exception` (since Python 3.8). This is
deliberate: a broad `except Exception:` handler — meant to catch *application* errors — must not
accidentally also catch and discard a cancellation request:

```python
import asyncio

async def leaky_cancel_handler() -> None:
    try:
        await asyncio.sleep(10)
    except Exception as e:
        # This does NOT match CancelledError — it inherits from BaseException.
        print(f"caught: {e!r}")

async def main() -> None:
    task = asyncio.create_task(leaky_cancel_handler())
    await asyncio.sleep(0.01)
    task.cancel()
    await task   # CancelledError propagates straight through — except Exception never ran

asyncio.run(main())
```

If you do need to intercept the cancellation for cleanup — closing a file, releasing a lock — catch
`asyncio.CancelledError` specifically, run the cleanup, and always finish with `raise` to let the
cancellation continue. Swallowing it (`except asyncio.CancelledError: pass`) leaves the task looking
"cancelled" to its caller while your code kept running past the cancellation point, which breaks the
guarantee `TaskGroup`/`wait_for`/`timeout()` all depend on.

## Debug mode and inspecting a running program (Python 3.14)

`asyncio.run(main(), debug=True)` (or the `PYTHONASYNCIODEBUG=1` environment variable) turns on
extra checks: it logs coroutines that were never awaited as they happen (not just at GC time), warns
when a callback blocks the loop for too long, and reports "Task was destroyed but it is pending".

When an async service hangs, the hard question is which coroutine is stuck. Python 3.14 can attach
to a *running* process and print its task tree — no instrumentation, no restart:

```bash
python -m asyncio ps 12345      # flat table of tasks in PID 12345
python -m asyncio pstree 12345  # the await tree
```

This rides on PEP 768's external debugger interface, which also lets `python -m pdb -p 12345` attach to a
live process. From inside your own code, `asyncio.capture_call_graph()` and `asyncio.print_call_graph()`
give the same picture for the current task.

## Mental Model

Picture the event loop as a single worker at a single desk with one in-tray. Every coroutine is a
task sitting in that tray. The worker picks up a task and works on it until it hits an `await` —
that is the coroutine saying "I'm waiting on something outside; put me back in the tray and work on
someone else in the meantime." The worker never works on two tasks at the literal same instant; it
just never sits idle waiting for one I/O operation when another task is ready to make progress.

This is also why one coroutine that never `await`s inside a long loop starves everyone else: the
worker cannot put a task down and switch away from it — only an `await` creates that opportunity.

## Trade-offs

| What you get | Benefit | Cost |
|---|---|---|
| Single-threaded event loop | No locks needed for code between `await` points | One slow, non-awaiting coroutine blocks everything else |
| `asyncio.gather` | Simple concurrent fan-out, minimal code | First exception cancels siblings unless `return_exceptions=True` |
| `TaskGroup` (3.11+) | Structured lifetimes, automatic sibling cancellation on failure | New API surface; `ExceptionGroup` needs `except*` to unpack |
| `async with` / `async for` | Setup/teardown and iteration can themselves `await` | A raw `async for` break can skip generator cleanup — needs `aclosing` |
| `-X dev` / debug mode | Surfaces never-awaited coroutines and slow callbacks immediately | Extra overhead — development/CI only, not production |

## Common Misconceptions

- **"`asyncio` gives you parallelism."** It gives you concurrency on a single thread. Two coroutines
  never run Python bytecode at the same instant; one always yields via `await` before the other
  proceeds.
- **"A `for` loop of `await` calls is already concurrent because it's async code."** It is not —
  each `await` in the loop body still blocks that iteration until it resolves. Only scheduling with
  `gather`/`TaskGroup`/`create_task` makes them overlap.
- **"`except Exception` is a safe catch-all in async code."** It silently misses
  `asyncio.CancelledError` — which is exactly correct for `Exception`'s contract, but a frequent
  surprise when someone expected it to catch "anything that goes wrong."
- **"Calling `asyncio.run` twice means nesting event loops."** Calling it twice, one after the other,
  at the top level is completely fine — each call gets an independent loop. Nesting means calling it
  **from inside** an already-running coroutine, which is a different (and always broken) thing.
- **"A never-awaited coroutine just wastes memory."** It also means the coroutine's *body never ran*
  — any side effect inside it (a write, a request, a state change) silently never happened.

## Reading AI-generated code

Before trusting generated `asyncio` code, check for these:

- Is every `async def` call actually `await`ed, `create_task`ed, or passed to `gather`/`TaskGroup`?
  A bare `coro_fn(...)` call with no `await` creates a coroutine object and does nothing else.
- Is there a broad `except Exception:` inside a coroutine that a `task.cancel()` could reach? If so,
  does it re-raise on `asyncio.CancelledError`, or does the generated code use a bare `except:` that
  swallows cancellation along with real bugs?
- Is a `for` loop `await`ing independent work one item at a time where `gather`/`TaskGroup` was
  clearly intended?
- Does an `async for` over a generator ever `break` early without `aclosing`?
- Is the code running under `-X dev` or `-W error::RuntimeWarning` in CI, so a forgotten `await`
  fails loudly instead of silently doing nothing?

<Callout title="await is the only place control changes hands">
Between two `await` expressions, a coroutine runs exactly like ordinary synchronous code — no other
coroutine can interleave. Concurrency in asyncio only happens *at* an `await`, and only when you
explicitly schedule more than one coroutine (`gather`, `TaskGroup`, `create_task`). A `for` loop of
sequential `await` calls is not concurrent just because the function is `async def`.
</Callout>
