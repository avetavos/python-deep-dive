Every output below is real, captured by running each tool against patterns from the **[AI Bug Catalog](/python/en/reading-python/ai-bug-catalog/)**. None of these tools overlap perfectly, and none of them is close to complete — the point of this lesson is to know exactly where each one's coverage ends, so you know what is still on you.

## `ruff` — one binary, linting and formatting, catches the most patterns for free

`ruff check` runs hundreds of rules (its own reimplementations of `pyflakes`, `pycodestyle`, `flake8-bugbear`, `bandit`'s security checks, `flake8-async`, and more) in one fast pass, with no per-plugin installation. Nine of this catalog's 24 patterns are caught by a `ruff` rule with zero configuration: `B006`, `B023`, `TRY201`, `S101`, `RUF006`, `ASYNC251`, `PLW1641`, `RUF012`, `DTZ003`, `SIM115`, `S602`, `T201`, plus the partial coverage on `F632` and the `E722`/`S110`/`BLE001` family for pattern #6.

**`ruff --fix` is safe by design — `--unsafe-fixes` is not.** `--fix` only applies rewrites `ruff` is confident preserve behavior. `--unsafe-fixes` applies rewrites that are usually right but can change meaning — and it does not ask before doing so. Real before/after on catalog pattern #1:

```python
# before
def add_item(item: str, cart: list[str] = []) -> list[str]:
    cart.append(item)
    return cart
```

```bash
ruff check --select B006 --fix --unsafe-fixes add_item.py
```

```python
# after -- ruff's own unsafe rewrite
def add_item(item: str, cart: list[str] = None) -> list[str]:
    if cart is None:
        cart = []
    cart.append(item)
    return cart
```

The rewrite does fix the runtime bug — but it left the parameter annotated `list[str]` while defaulting it to `None`, which is not the same fix a careful human would write (`list[str] | None = None`). Running `mypy --strict` on the *rewritten* file, unmodified:

```text
error: Incompatible default for parameter "cart" (default has type "None", parameter has type "list[str]")  [assignment]
note: PEP 484 prohibits implicit Optional. Accordingly, mypy has changed its default to no_implicit_optional=True
```

`--unsafe-fixes` traded one real bug for one real type error, silently, in one automated pass. Always re-run your type checker (and read the diff) after `--unsafe-fixes` — never run it unattended in CI.

## `mypy --strict` vs `pyright` — real agreement, and a real disagreement

Both are static type checkers that read the same annotations, and they usually agree — but "usually" is not "always," and a reviewer who only runs one can be misled by the other's blind spot.

**Real agreement**, on catalog pattern #17 (`Optional` not narrowed):

```text
mypy --strict:  error: Item "None" of "str | None" has no attribute "upper"  [union-attr]
pyright:        error: "upper" is not a known attribute of "None" (reportOptionalMemberAccess)
```

**Real agreement**, on catalog pattern #18 (list invariance):

```text
mypy --strict:  error: Argument 1 to "add_a_cat" has incompatible type "list[Dog]"; expected "list[Animal]"  [arg-type]
pyright:        error: Argument of type "list[Dog]" cannot be assigned to parameter "animals" of type "list[Animal]" (reportArgumentType)
```

**Real disagreement**, on a one-line status check that AI code writes constantly:

```python
def is_ready(status: int) -> bool:
    return status == "ready"
```

```text
mypy --strict:  error: Non-overlapping equality check (left operand type: "int", right operand type: "Literal['ready']")  [comparison-overlap]
pyright:        0 errors, 0 warnings, 0 informations
```

`mypy --strict` bundles `--strict-equality`, which flags a comparison between two types that can never actually be equal — `status` is always an `int`, `"ready"` is always a `str`, so `status == "ready"` is always `False` and almost certainly a bug (comparing the wrong variable, or against the wrong literal). `pyright` has no equivalent check enabled by default and is completely silent on this exact file. Running only `pyright` in CI would ship this bug; running only `mypy --strict` would have caught it.

**Real, complete silence — both tools, one file**, on catalog pattern #16 (`Any` plus a blanket `# type: ignore`):

```text
mypy --strict:  Success: no issues found in 1 source file
pyright:        0 errors, 0 warnings, 0 informations
```

Neither tool has anything to say about a runtime `AttributeError` waiting on the very next line — `Any` is a deliberate escape hatch from both type systems, not a gap in either implementation.

<Callout title="Run both, and read what neither one flags">
`mypy --strict` and `pyright` disagree often enough (different default strictness knobs, different treatment of narrowing, different opt-in checks like `--strict-equality`) that running only one is a real coverage gap, not just redundant caution. Where they *both* stay silent — any `Any`, any `# type: ignore` — is exactly where the **[Review Checklist](/python/en/reading-python/review-checklist/)**'s typing section exists to catch what neither tool can.
</Callout>

## `python -X dev` / `-W error` — the only tools that watch the program run

`python3.14 -X dev` enables Python's development mode: extra runtime assertions, `ResourceWarning`s for unclosed files, `asyncio` debug mode (slow-callback logging), and — critically for this catalog — the `RuntimeWarning: coroutine '...' was never awaited` message the moment an abandoned coroutine is garbage-collected. `-W error::RuntimeWarning` (used by this course's own verifier) additionally turns that warning into a raised exception wherever it is not already inside a `warnings.catch_warnings()` block.

**Real output**, catalog pattern #9 (never-awaited coroutine):

```text
Exception ignored while finalizing coroutine <coroutine object greet at 0x...>:
RuntimeWarning: coroutine 'greet' was never awaited
```

**Real output**, catalog pattern #19 (`datetime.utcnow()`):

```text
DeprecationWarning: datetime.datetime.utcnow() is deprecated and scheduled for removal in a future version. Use timezone-aware objects to represent datetimes in UTC: datetime.datetime.now(datetime.UTC).
```

**Misses:** everything that requires the exact code path to actually execute during that run. A never-awaited coroutine that is never garbage-collected during a short script's lifetime, or a race condition that happens not to interleave badly on this particular run, produces no warning at all — `-X dev` proves the presence of a problem it observed, never the absence of one it didn't happen to trigger.

## `pytest` + coverage — tells you what was never run, not what is broken

```python
def withdraw(balance: int, amount: int) -> int:
    if amount > balance:
        raise ValueError("insufficient funds")
    return balance - amount
```

```python
def test_withdraw_success():
    assert withdraw(100, 30) == 70
```

**Real output**, `pytest --cov=account --cov-report=term-missing`:

```text
.                                                                        [100%]
Name         Stmts   Miss  Cover   Missing
------------------------------------------
account.py       4      1    75%   3
------------------------------------------
TOTAL            4      1    75%
1 passed in 0.01s
```

The one test passes, and coverage is 75% — the missing 25% is exactly line 3, the `raise ValueError` branch. Coverage did not find a bug in that line; it found that nobody had tested it at all, which is a different (and weaker) guarantee.

**Misses:** correctness entirely. 100% coverage proves every line ran at least once during some test — it proves nothing about whether the assertions in that test were the right ones, or whether the specific input that triggers a bug (like the race in catalog pattern #12) was ever tried. See **[Worked Review 4](/python/en/reading-python/worked-review-4/)** for a full suite that passes at high coverage while several real bugs ship untouched.

## `bandit` — security-focused static analysis, overlaps `ruff`'s `S` rules on purpose

`bandit` predates `ruff`'s security rule port and remains useful as an independent second opinion, or where a project cannot yet adopt `ruff`. On this catalog it flags the same underlying issues `ruff`'s `S`-prefixed rules do, under its own `B`-numbered codes:

```text
>> Issue: [B101:assert_used] Use of assert detected. The enclosed code will be removed when compiling to optimised byte code.
>> Issue: [B602:subprocess_popen_with_shell_equals_true] subprocess call with shell=True identified, security issue.
>> Issue: [B404:blacklist] Consider possible security implications associated with the subprocess module.
```

**Misses:** anything outside its security-focused rule set — logic bugs, mutability bugs, and most of the async patterns in this catalog are entirely out of scope for `bandit` by design.

## `pip-audit` (or `uv`'s equivalent) — known CVEs in your exact pinned versions

```text
requirements.txt:
requests
urllib3==1.26.4
```

**Real `pip-audit -r requirements.txt` output:**

```text
Found 18 known vulnerabilities in 1 package
Name    Version ID              Fix Versions
------- ------- --------------- -------------
urllib3 1.26.4  PYSEC-2021-108  1.26.5
urllib3 1.26.4  PYSEC-2023-192  1.26.17,2.0.6
urllib3 1.26.4  PYSEC-2023-212  1.26.18,2.0.7
...
```

**Misses:** your own code entirely. `pip-audit` answers one question only — "does a known, published vulnerability affect a package version I have pinned" — and has nothing to say about logic bugs, concurrency bugs, or API misuse, whether in your code or in a dependency's undiscovered (not-yet-published) vulnerabilities. It also cannot catch an *unpinned* requirement going stale in the other direction, or `sudo pip install` polluting a system Python — see catalog pattern #23.

<SpotTheBug code={`# requirements.txt
django>=4.0`}>

Nothing here is syntactically wrong, and `pip-audit` may well report zero known vulnerabilities against whatever `>=4.0` happens to resolve to today. That is exactly the trap: an unpinned lower bound means the *same file* can resolve to a different, newer major version next month, with no vulnerability necessarily involved at all — just a behavior change nobody asked for at install time. `uv lock` (or `pip-compile`) turns this into an exact, reproducible pin; re-run the audit tool against every lockfile update, not just once.

</SpotTheBug>

## Running the whole ladder in one command

Each tool covers a different, non-overlapping slice of this catalog. Chained with `&&`, the command stops at the first tool that finds something — real output, run against catalog pattern #17's file, stopping at `mypy`:

```bash
ruff check . && mypy --strict . && pyright . && bandit -q -r . && pytest --cov
```

```text
All checks passed!
file.py:2: error: Item "None" of "str | None" has no attribute "upper"  [union-attr]
Found 1 error in 1 file (checked 1 source file)
```

`ruff` passed; `mypy --strict` caught the bug and the chain stopped there — exactly the fail-fast behavior you want in a pre-commit hook or CI gate. Add `pip-audit -r requirements.txt` as a separate, periodic step (dependency vulnerabilities change over time even when your code doesn't).
