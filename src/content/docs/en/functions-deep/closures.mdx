## Nested functions

Python allows you to define a function inside another function.
The inner function has access to variables in the enclosing (outer) function's scope.

```python
def outer():
    message = "Hello from outer"

    def inner():
        print(message)   # accesses the enclosing scope

    inner()

outer()  # Hello from outer
```

## LEGB: how Python looks up a name

Every name lookup in Python follows one fixed order, abbreviated **LEGB**:

1. **Local** — names assigned inside the current function
2. **Enclosing** — names in any enclosing function's local scope (this is where closures live)
3. **Global** — names assigned at module level
4. **Built-in** — names Python provides itself (`len`, `print`, `range`, ...)

Python stops at the first scope where the name is found:

```python
x = "global x"

def legb_demo():
    y = "enclosing y"

    def inner():
        z = "local z"
        print("local:", z)
        print("enclosing:", y)   # not local to inner — found in legb_demo's scope
        print("global:", x)      # not local or enclosing — found at module level
        print("built-in:", len)  # not any of the above — found in builtins
    inner()

legb_demo()
```

## Free variables and closures

When an inner function **references a variable from its enclosing scope** and is then **returned** to the outside world,
Python creates a **closure** — the inner function "closes over" the variable and keeps it alive even after `outer` has finished executing.

```python
def make_greeter(greeting: str):
    def greet(name: str) -> str:
        return f"{greeting}, {name}!"   # greeting is a free variable
    return greet

hello = make_greeter("Hello")
hi    = make_greeter("Hi")

print(hello("Alice"))   # Hello, Alice!
print(hi("Bob"))        # Hi, Bob!
```

`greeting` is a **free variable** in `greet` — it is not defined inside `greet` and not a global; it lives in `make_greeter`'s local scope, one level up in the "E" of LEGB.
The closure keeps the value of `greeting` alive for as long as `hello` or `hi` exist.

## `__closure__` and cell contents

A closure is not magic — CPython implements it with **cell objects**, one per free variable, stored on the function's `__closure__` tuple. `__code__.co_freevars` names which variables those cells hold:

```python
def make_greeter(greeting):
    def greet(name):
        return f"{greeting}, {name}!"
    return greet

hello = make_greeter("Hello")
print(hello.__closure__[0].cell_contents)   # Hello
print(hello.__code__.co_freevars)           # ('greeting',)
```

Each call to `make_greeter` creates a fresh cell — `hello` and `hi` from the earlier example have completely independent cells, which is why they remember different greetings.

## The `nonlocal` keyword

Inside a nested function, you can **read** a free variable without any special keyword.
But to **reassign** it, you need `nonlocal` — otherwise Python treats the name as a new local variable.

```python
def make_counter(start: int = 0):
    count = start

    def increment(step: int = 1) -> int:
        nonlocal count        # tells Python: reuse the enclosing 'count'
        count += step
        return count

    def reset() -> None:
        nonlocal count
        count = start

    return increment, reset

inc, rst = make_counter()
print(inc())    # 1
print(inc())    # 2
print(inc(5))   # 7
rst()
print(inc())    # 1
```

Without `nonlocal count`, the line `count += step` would raise `UnboundLocalError` because Python sees the assignment and treats `count` as a local variable that has not been assigned yet.

## `global`: the same rule, one scope further out

`global` is `nonlocal`'s counterpart for module-level names: it tells Python that an assignment inside a function should rebind the **global** name instead of creating a new local one. The same `UnboundLocalError` rule applies without it — Python decides a name is local to a function by scanning the *whole function body* for assignments, before running any of it, so even reading the name before the assignment line fails:

```python
counter = 0

def increment_global():
    global counter
    counter += 1

increment_global()
increment_global()
print(counter)   # 2

def broken_increment():
    counter += 1   # counter is assigned somewhere in this function...
                    # ...so Python treats it as local for the *entire* function body

broken_increment()
# UnboundLocalError: cannot access local variable 'counter' where it is not associated with a value
```

`global` and `nonlocal` solve the same problem (an assignment would otherwise create a shadowing local) at two different scope distances — `global` always reaches module scope directly, skipping any enclosing function scopes in between; `nonlocal` reaches the nearest enclosing *function* scope.

## Closing over a mutable instead of using `nonlocal`

Reassigning a free variable requires `nonlocal`, but **mutating** an object the closure already holds a reference to does not — this is often the simpler fix when several inner functions need to share state:

```python
def make_counter_mutable():
    state = {"count": 0}   # mutable container — no nonlocal needed

    def increment(step: int = 1) -> int:
        state["count"] += step   # mutating the dict, not rebinding the name
        return state["count"]

    return increment, state

inc, state = make_counter_mutable()
print(inc())      # 1
print(inc(5))     # 6
print(state)       # {'count': 6} — visible from outside too
```

`state["count"] += step` looks up `state` (read-only access to the free variable — no `nonlocal` needed) and then mutates the dict it points to. This trades `nonlocal`'s explicit reassignment for a shared mutable container — useful when multiple inner functions need to observe or reset the same state, but it also exposes that state directly to any code holding a reference to `state`, which `nonlocal`'s fully private cell does not.

## Trade-offs

| What you get | Benefit | Cost |
|---|---|---|
| `nonlocal` | Explicit, self-documenting reassignment of an enclosing variable | Must be declared before the first assignment in the function; forgetting it raises `UnboundLocalError`, not a silent wrong answer |
| Closing over a mutable (dict/list) | No `nonlocal` needed to share state across several inner functions | The state is a plain object anyone holding a reference to it can mutate from outside too — no privacy `nonlocal`'s cell gives you |
| `global` | Lets a function update true module-level state | Couples the function to a specific module's global; makes the function harder to test in isolation and to reason about from other modules |
| Default-argument late-binding fix (`lambda i=i: ...`) | One extra `=i`, no imports needed | Easy to forget; reads oddly to someone unfamiliar with the idiom |
| `functools.partial` late-binding fix | Explicit and self-documenting — freezes the argument by name | Requires an extra `import functools` and a named function instead of an inline `lambda` |

## Common Misconceptions

- **"A closure captures the value a variable had when the function was defined"** — fact: it captures the **variable itself** (the cell) — if that variable's value changes later, every closure over it sees the new value, which is exactly why the late-binding loop gotcha happens.
- **"Reading an enclosing variable requires `nonlocal`, same as writing it"** — fact: `nonlocal` is only needed to **reassign** a free variable. Reading it, or mutating an object it refers to (`state["count"] += 1` on a dict), needs no declaration at all.
- **"`UnboundLocalError` means the variable was never given a value anywhere"** — fact: it means Python decided the name is local to *this* function (because it is assigned somewhere in the function body) and that particular execution reached a read before the local assignment ran — the exact failure mode of forgetting `global`/`nonlocal`.
- **"Two closures created from the same factory function share state"** — fact: each call to the factory (`make_greeter("Hello")` vs `make_greeter("Hi")`) creates its own independent cell — closures from different calls never see each other's variables unless they explicitly share a mutable object.
- **"The late-binding loop bug only affects `lambda`"** — fact: any nested function defined in a loop and capturing the loop variable has the same bug, `lambda` is just the shortest way to demonstrate it.

## Reading AI-generated code

- Does a nested function assign to a variable from an enclosing scope without `nonlocal` (or the module's global without `global`)? Either it is a bug (`UnboundLocalError` waiting to happen) or the author actually wanted a fresh local variable — check which.
- Are functions or lambdas being created inside a loop, closing over the loop variable, and called *after* the loop finishes? Check for the late-binding gotcha — every one of them will see the loop variable's *final* value.
- Is shared mutable state (a dict or list) closed over by several inner functions instead of `nonlocal`? Confirm that sharing is intentional and that nothing outside the closure can corrupt it unexpectedly.
- Does a function read a name that is assigned later in the *same* function body, expecting to see a global or enclosing value first? Python decides "local" for the whole function ahead of time — this raises `UnboundLocalError`, not a fallback to the outer scope.
- Is `global` used where the value could instead be threaded through function parameters and return values? Excess `global` usage makes functions hard to test and to reason about without reading the whole module.

The fix is to freeze the current value at definition time, either with default arguments (\`def handler(i=i, label=label): ...\`) or with \`functools.partial(handler_body, i, label)\` — both evaluate \`i\`/\`label\` immediately, once per loop iteration, instead of looking them up later through the shared closure cell.

<Callout title="Closures capture variables, not values">
The late-binding gotcha: closures capture the **variable** itself, not the value it held when the closure was created.
In a loop this bites hard:

```python
# WRONG — all functions capture the same variable i
funcs = [lambda: i for i in range(3)]
print([f() for f in funcs])   # [2, 2, 2]  (all see the final i)

# RIGHT — bind the current value as a default argument
funcs = [lambda i=i: i for i in range(3)]
print([f() for f in funcs])   # [0, 1, 2]
```

The default-argument trick `i=i` evaluates `i` at **definition time**, creating a fresh binding for each function. `functools.partial(lambda i: i, i)` inside the loop achieves the same freeze, more explicitly.
</Callout>
