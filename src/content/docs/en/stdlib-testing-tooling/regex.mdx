## Raw strings, and why regex patterns almost always use them

A regex pattern is written as a normal Python string first, then handed to the `re` engine, which does its *own* second pass of interpreting backslashes (`\d` means "a digit" to `re`, not to Python). Without a raw string, Python's own string parser eats the backslash first.

```python
print("\d+")   # Python sees an unrecognised escape -- see the warning below
print(r"\d+")  # raw string: the backslash reaches re untouched
```

Since Python 3.12, an unrecognised escape sequence inside a normal (non-raw) string literal is a `SyntaxWarning`, not silence:

```text
$ python3.14 -c 'pattern = "\d+"; print(pattern)'
<string>:1: SyntaxWarning: "\d" is an invalid escape sequence. Such sequences will not work in
the future. Did you mean "\\d"? A raw string is also an option.
  pattern = "\d+"; print(pattern)
\d+
```

The program still runs — `\d` happens to fall back to a literal backslash followed by `d`, so this *particular* pattern is accidentally still correct — but that is luck, not design. `\n`, `\t`, and a handful of others are recognised Python escapes and would silently change meaning instead of warning. The fix is always the same: prefix the string with `r` the moment it is a regex pattern, full stop, no exceptions.

> This SyntaxWarning is a compile-time diagnostic from Python's own string parser, not a `RuntimeWarning` — it will not turn into an exception in a Playground below (which only escalates `RuntimeWarning` to an error), so it is shown here as a real terminal transcript instead.

## `re.compile` and the module cache

`re.compile(pattern)` returns a reusable `Pattern` object with `.match`/`.search`/`.findall`/etc. methods. The module-level functions (`re.search(pattern, text)`, `re.findall(pattern, text)`, ...) are convenience wrappers that call `re.compile` internally — and `re.compile` itself is backed by a small cache (`re._MAXCACHE` entries, keyed by the exact pattern text and flags), so calling it repeatedly with the same arguments does not recompile:

export const pg1Code = `
import re

# re.compile is cached: same pattern text + same flags returns the SAME object
a = re.compile(r"\\d+")
b = re.compile(r"\\d+")
print("cache hit (identical pattern+flags):", a is b)

c = re.compile(r"\\d+", re.IGNORECASE)
print("cache miss (different flags):", a is c)

# Five ways to look for the same pattern in the same text
pattern = re.compile(r"\\d+")
text = "room 12, hall 345, gate 6"

print("match:    ", pattern.match(text))       # anchored at index 0 only
print("search:   ", pattern.search(text))      # first match anywhere
print("fullmatch:", pattern.fullmatch(text))    # entire string must match
print("fullmatch (digits only):", pattern.fullmatch("789"))
print("findall:  ", pattern.findall(text))      # every match, as strings
print("finditer: ", [m.group() for m in pattern.finditer(text)])  # every match, as Match objects
`.trim();

<Playground code={pg1Code} />

Explicit `re.compile` still matters for readability and for attaching flags once instead of at every call site — but "compile once at module scope for performance" is largely folklore since 3.x: the cache already does that for you as long as the pattern text and flags stay identical.

## `match` vs `search` vs `fullmatch` vs `findall` vs `finditer`

The five ways to look for a pattern in a string differ only in **where** they require the match, and **what** they hand back:

<Mermaid code={`flowchart LR
  Text["text = 'concatenate', pattern = re.compile('cat')"] --> M["pattern.match(text) -- checks only index 0 -- None"]
  Text --> S["pattern.search(text) -- scans left-to-right -- finds 'cat' at index 3"]
  Text --> F["pattern.fullmatch(text) -- requires the ENTIRE string -- None"]`} title="match / search / fullmatch: same pattern, three different anchoring rules" />

`match` and `fullmatch` are anchored (implicitly at the start; `fullmatch` also at the end); `search` is not anchored at all. `findall` returns every match as plain strings (or tuples, if the pattern has groups); `finditer` returns every match as lazy `Match` objects, so you keep access to `.start()`, `.end()`, and `.groups()` for each one.

## Groups, named groups, and `groupdict`

Parentheses `(...)` capture a sub-match; `(?P<name>...)` names it, so you don't have to remember positional indices when reading the result later.

## Greedy vs lazy quantifiers

`*`, `+`, and `{m,n}` are **greedy** by default: they grab as much as possible, then give characters back only if the rest of the pattern needs them to. Adding `?` after a quantifier (`*?`, `+?`, `{m,n}?`) makes it **lazy**: grab as little as possible, then expand only if needed.

export const pg2Code = `
import re

m = re.search(r"(\\d{4})-(\\d{2})-(\\d{2})", "created: 2026-09-22")
print("groups:", m.groups())
print("group 1:", m.group(1))

named = re.search(r"(?P<year>\\d{4})-(?P<month>\\d{2})-(?P<day>\\d{2})", "created: 2026-09-22")
print("groupdict:", named.groupdict())

# Greedy vs lazy on the same text
html = "<b>bold</b> and <i>italic</i>"
greedy = re.search(r"<.*>", html)
lazy = re.search(r"<.*?>", html)
print("greedy:", greedy.group())
print("lazy:  ", lazy.group())
`.trim();

<Playground code={pg2Code} />

The greedy `<.*>` grabs from the first `<` all the way to the *last* `>` in the string, swallowing everything in between — almost never what you want against HTML-like text. The lazy `<.*?>` stops at the first `>` it can get away with.

## Flags: `re.I`, `re.M`, `re.S`, `re.X`

export const pg3Code = `
import re

print(bool(re.search(r"python", "I love PYTHON", re.I)))

text = "line1\\nline2\\nline3"
print(re.findall(r"^line\\d", text, re.M))

print(bool(re.match(r"a.b", "a\\nb", re.S)))

pattern = re.compile(
    r"""
    (?P<area>\\d{3})   # area code
    -
    (?P<num>\\d{4})    # local number
    """,
    re.X,
)
m = pattern.search("call 555-1234 now")
print(m.groupdict())
`.trim();

<Playground code={pg3Code} />

`re.I` (`IGNORECASE`) folds case. `re.M` (`MULTILINE`) makes `^`/`$` match at every line boundary, not just the start/end of the whole string. `re.S` (`DOTALL`) makes `.` also match `\n` (by default it does not). `re.X` (`VERBOSE`) ignores whitespace and lets you write `#` comments inside the pattern itself — the single biggest readability win for any pattern with more than two or three parts, and it's the reason the phone-number pattern above is legible at all.

## `re.sub` with a callable and with backreferences

The replacement argument to `re.sub` can be a plain string with backreferences (`\1`, `\2`, ...) referring to captured groups, or a function that receives the `Match` object and returns the replacement text — needed whenever the replacement depends on what was matched, not just a fixed rearrangement.

export const pg4Code = `
import re

# Backreference: swap "first last" to "last, first"
print(re.sub(r"(\\w+) (\\w+)", r"\\2, \\1", "John Smith"))

# Callable: shout every word, using a function instead of a static replacement
def upper_word(m: re.Match) -> str:
    return m.group().upper()

print(re.sub(r"\\b\\w+\\b", upper_word, "make this shout"))

# re.escape: safe substring search built from untrusted input
user_input = "3.14 (pi)"
print(bool(re.search(re.escape(user_input), "value is 3.14 (pi) exactly")))
print(bool(re.search(user_input, "value is 3.14 (pi) exactly")))  # unescaped: . and () mean something else
`.trim();

<Playground code={pg4Code} />

The last two lines are the important contrast: with `re.escape`, every regex-special character in `user_input` is treated literally, and the search finds the exact substring. Without it, `.` means "any character" and `(pi)` is parsed as a capturing group around the letters `pi` — the parentheses themselves are *not* literal characters to match, so the pattern actually requires the literal text `"pi"` to appear immediately after `"3X14 "` with **no** `(` in between. It doesn't; the real text has `"(pi)"`, not `"pi"` right after the space — so the unescaped search returns `False`, silently, with no exception to warn you the pattern meant something different from what was typed. **Any user-supplied string used to build a regex pattern must go through `re.escape` first**, unless the whole point is to let the user write a pattern.

## Catastrophic backtracking

A pattern like `(a+)+b` looks harmless, but nesting two "one or more" quantifiers over overlapping input creates an enormous number of equivalent ways to split the string between the inner and outer group — and when the trailing `b` never shows up, the engine tries *all* of them before giving up. The number of ways to split `n` characters grows exponentially with `n`:

export const pg5Code = `
import re
import time

# (a+)+b : two nested "one or more" quantifiers over the same character class.
# For a string of all "a" with no trailing "b", the engine tries every way to
# split the a-run between the inner and outer "+" before giving up -- that
# splitting count grows exponentially with the input length.
evil = re.compile(r"(a+)+b")

print("catastrophic pattern (a+)+b -- timing grows fast:")
for n in (20, 22, 24):
    text = "a" * n
    start = time.perf_counter()
    result = evil.match(text)
    elapsed = time.perf_counter() - start
    print(f"  n={n:2d}  match={result}  {elapsed:.4f}s")

# Fix 1: possessive quantifier \`*+\` (3.11+) -- once the outer group grabs
# characters, it never gives them back to try another split.
possessive = re.compile(r"(a+)*+b")

# Fix 2: atomic group \`(?>...)\` (3.11+) -- same idea, wraps the whole
# backtracking-prone group so its internal choices are never revisited.
atomic = re.compile(r"(?>(a+)+)b")

print("\\nfixed with possessive quantifier / atomic group -- flat timing:")
for name, fixed in (("possessive (a+)*+b", possessive), ("atomic (?>(a+)+)b", atomic)):
    for n in (20, 22, 24):
        text = "a" * n
        start = time.perf_counter()
        result = fixed.match(text)
        elapsed = time.perf_counter() - start
        print(f"  {name:20s} n={n:2d}  match={result}  {elapsed:.6f}s")
`.trim();

<Playground code={pg5Code} />

Real timings on this course's dev machine (yours will differ, but the *shape* is the point): the catastrophic version took roughly 0.03s at 20 characters, 0.11s at 22, and 0.47s at 24 — each two extra characters multiplies the time by about 4x, so 40 characters would already take minutes and 60 would not finish in a reasonable lifetime. Both fixed versions finished in well under a millisecond at every length tested (machine-dependent, but the flatness — not the exact numbers — is what proves the fix). Possessive quantifiers (`*+`, `++`, `{m,n}+`) and atomic groups (`(?>...)`) have been supported by `re` since Python 3.11: both tell the engine "once this group matches, never come back and try a different split of it" — which is exactly the choice that was exploding combinatorially before.

This is not a rare edge case: any pattern shaped like `(X+)+`, `(X*)*`, or `(X|XY)+` against a long non-matching or almost-matching input is a candidate. If a pattern is built from user input, or matches against user input, catastrophic backtracking is a real denial-of-service vector, not just a performance curiosity.

## When `str` methods beat regex

Regex is overkill — slower to write, slower to read, and often slower to run — for checks that a plain string method already expresses directly:

export const pg6Code = `
import re

path = "/api/v2/users"

# str methods beat regex for fixed, literal checks
print(path.startswith("/api/"))
print(path.split("/"))
print(path.removeprefix("/api/v2"))
print("users" in path)

# unicode \\w matches more than ASCII letters/digits/underscore
print(re.findall(r"\\w+", "café münchen 42"))
print(re.findall(r"[A-Za-z0-9_]+", "café münchen 42"))
`.trim();

<Playground code={pg6Code} />

`startswith`/`endswith` beat `re.match(r"^literal")`; `split` beats a regex with no actual pattern in it; `removeprefix`/`removesuffix` (3.9+) beat a regex used only to strip a fixed literal string; plain `in` beats `re.search` for a literal substring check. Reach for `re` when the thing you're looking for has *variation* a plain string operation can't express — a shape, not a fixed value.

The unicode result above is also worth internalising: `\w` under `re`'s default (unicode) mode matches any character Unicode classifies as a "word" character — accented Latin letters included — not just `[A-Za-z0-9_]`. Code that assumes `\w` is ASCII-only silently mishandles non-English text.

## Regex smells in AI-generated code

- `re.match` used where the intent is "does this pattern appear anywhere" — `re.match` only checks the start of the string; `re.search` is almost always the one that was meant.
- A pattern built by string-concatenating or f-string-interpolating a variable that came from user input, without `re.escape` around that variable.
- A nested quantifier shape like `(.*)*`, `(a+)+`, or `(\w*)*` — a catastrophic-backtracking candidate, especially if the input can come from outside the program.
- A plain (non-raw) string used as a regex pattern — no `r` prefix — relying on the fact that most escape sequences happen not to collide with a recognised Python one.
- `re.compile` re-created inside a hot loop with a genuinely dynamic pattern, treated as if it must be hoisted for performance — the module cache already makes this mostly moot unless the pattern text itself changes every call.
- A regex used to validate or parse something with a real parser already in the stdlib (URLs, JSON, dates, file paths) — regex handles *lexical* patterns, not nested/recursive structure.

## Reading AI-generated code

Before trusting a generated regex, check for:

- `re.match` used to find a substring that is not guaranteed to be at index 0 — silently returns `None` for perfectly valid input that just doesn't start with the pattern.
- A pattern assembled from unescaped user input — a metacharacter in that input changes what the pattern actually means, and `re.escape` is the fix.
- Nested quantifiers over the same character class (`(.*)*`, `(a+)+`) — a catastrophic-backtracking risk that only shows up once the input is long enough.
- A regex pattern string missing the `r` prefix.

## Mental Model

A regex engine is a tiny virtual machine that tries to walk a pattern and a string in lockstep, backtracking (undoing a greedy choice and trying a shorter one) whenever the rest of the pattern fails to match what's left. `match`/`search`/`fullmatch` only change *where* that walk is allowed to start and end; the walking-and-backtracking machinery underneath is identical for all three. Catastrophic backtracking is what happens when the pattern gives the engine many equally-valid ways to have arrived at the same position — it doesn't remember "I already tried this," so it repeats work exponentially.

## Trade-offs

| What you get | Benefit | Cost |
|---|---|---|
| `re.search` over `re.match` as the default | Matches the actual intent ("is this pattern present") in almost every case | `match`'s anchoring is easy to forget is even a restriction until it silently returns `None` |
| `re.compile` at module scope | Readable, one place to see the flags | Mostly a style/readability win now — the internal cache already avoids recompiling identical (pattern, flags) pairs |
| `re.X` (verbose) patterns | Self-documenting, comments allowed inline | Whitespace inside the pattern must be explicitly escaped (`\ ` or `[ ]`) since literal spaces are ignored |
| Possessive quantifiers / atomic groups | Eliminates catastrophic backtracking for the wrapped group | The wrapped group can no longer backtrack *at all* — a pattern that relied on that backtracking to match valid input can start failing |
| Plain `str` methods over regex | Faster, more readable for fixed/literal checks | Cannot express variation (character classes, repetition, alternation) — reach for `re` the moment the target has a *shape*, not a fixed value |

## Common Misconceptions

- **"`re.match` checks whether the pattern appears in the string."** It only checks the *start* of the string. `re.search` checks anywhere; `re.match(pattern, s)` behaves like `re.search(f"^{pattern}", s)` (with `re.M` off).
- **"A pattern without an `r` prefix is fine as long as it looks correct."** It's fine only by coincidence — the moment the pattern needs `\n`, `\t`, or any other recognised Python string escape, the meaning silently changes instead of reaching `re` as written.
- **"Compiling a pattern with `re.compile` inside a function is a performance mistake."** The module-level cache already deduplicates identical `(pattern, flags)` pairs; the real cost of *not* using `re.compile` is readability (flags repeated at every call site), not repeated compilation.
- **"`\w` only matches `[A-Za-z0-9_]`."** By default `re` operates in unicode mode, and `\w` matches any character Unicode classifies as alphanumeric, not just ASCII — verified above with `café münchen`.
- **"Catastrophic backtracking is a theoretical concern, not a real bug."** The timings above are real, measured, and grow from milliseconds to minutes to longer than a human lifetime with a linear increase in input length — this is a genuine denial-of-service vector for any pattern shaped like `(X+)+` fed attacker-controlled input.
