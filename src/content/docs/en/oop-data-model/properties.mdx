## The `@property` decorator

`@property` turns a method into an attribute-style accessor.
Callers use `obj.celsius` instead of `obj.get_celsius()`, keeping the public API clean while allowing validation logic to run behind the scenes.

```python
class Temperature:
    def __init__(self, celsius: float = 0.0) -> None:
        self._celsius = celsius    # underscore = internal storage

    @property
    def celsius(self) -> float:
        return self._celsius
```

## Setters

Pair `@property` with `@name.setter` to intercept assignment:

```python
    @celsius.setter
    def celsius(self, value: float) -> None:
        if value < -273.15:
            raise ValueError("Temperature below absolute zero!")
        self._celsius = value
```

Now `t.celsius = -300` raises `ValueError` automatically.
Without a setter, the property is read-only — attempts to assign raise `AttributeError`.

## Computed (derived) properties

A property can compute its value on the fly with no backing storage:

```python
    @property
    def fahrenheit(self) -> float:
        return self._celsius * 9 / 5 + 32
```

`t.fahrenheit` looks like a plain attribute to the caller, but it is recalculated each time.

## `property` *is* a descriptor — write your own in 10 lines

`@property` is not special syntax the interpreter hard-codes — it is a class, `property`, that implements the **descriptor protocol**: `__get__`, `__set__`, and optionally `__delete__`. Any class that implements those methods and is stored as a *class* attribute behaves the same way. Here is a hand-written descriptor that reimplements the validating `celsius` property from scratch, in about ten lines:

```python
class Celsius:
    def __set_name__(self, owner: type, name: str) -> None:
        self.name = f"_{name}"          # remembers the attribute name it's bound to

    def __get__(self, obj: object, objtype: type | None = None) -> float:
        if obj is None:
            return self                  # accessed on the class itself, e.g. Thermostat.celsius
        return getattr(obj, self.name, 0.0)

    def __set__(self, obj: object, value: float) -> None:
        if value < -273.15:
            raise ValueError("Temperature below absolute zero!")
        setattr(obj, self.name, value)


class Thermostat:
    celsius = Celsius()   # a descriptor instance, used exactly like @property
```

`t.celsius = 21.0` calls `Celsius.__set__`; `t.celsius` calls `Celsius.__get__` — identical behavior to `@property` with a setter, because that's genuinely what `property` is under the hood: `hasattr(property, "__get__")` and `hasattr(property, "__set__")` are both `True`. Understanding this explains a lot of "surprising" behavior elsewhere in Python: `classmethod`, `staticmethod`, and functions themselves (bound methods) are all descriptors too — attribute access on an instance is really the descriptor protocol running, every time.

## `functools.cached_property`

A `@property` recomputes on every access. `@cached_property` (from `functools`) computes the value once, on first access, and stores it as a plain entry in the instance's `__dict__` — every access after that is a normal (fast) attribute lookup, not a re-run of the method:

```python
from functools import cached_property

class Report:
    def __init__(self, rows: list[int]) -> None:
        self.rows = rows

    @cached_property
    def total(self) -> int:
        return sum(self.rows)   # only runs once per instance
```

`r.total` accessed twice runs the summing method exactly once; `r.__dict__["total"]` shows the cached result sitting there as an ordinary attribute after the first access. Because the cache lives in `__dict__`, a `cached_property` requires the instance to have one (it will not work on a `slots=True` class unless `"total"` is listed as a slot) — and since the cache is just an instance attribute, invalidating it is `del obj.total`, which forces the next access to recompute.

## `@classmethod` — alternative constructors

A class method receives the **class** (`cls`) as its first argument instead of the instance.
The most common use is providing alternative constructors:

```python
    @classmethod
    def from_fahrenheit(cls, f: float) -> Self:
        return cls((f - 32) * 5 / 9)
```

```python
boiling = Temperature.from_fahrenheit(212)
print(boiling.celsius)   # 100.0
```

Subclasses automatically inherit the class method and `cls` will refer to the subclass — so the factory creates an instance of the correct type.
Annotate the return type with `typing.Self` (`from typing import Self`), not the string literal `"Temperature"` — the string annotation makes a type checker infer the base class even when `cls` is a subclass. With the old annotation, `uvx mypy --strict` on a subclass that adds a method reports exactly this: `` "Temperature" has no attribute "to_kelvin"  [attr-defined] ``. `Self` fixes it because it always refers to whatever class the method was actually called on — confirmed with a real subclass:

```python
class Kelvin(Temperature):
    def to_kelvin(self) -> float:
        return self.celsius + 273.15

k = Kelvin.from_fahrenheit(32)
print(type(k))       # <class '__main__.Kelvin'>
print(k.to_kelvin())  # 273.15 -- only type-checks because from_fahrenheit's return type is Self
```

`k` really is a `Kelvin` at runtime regardless of the annotation — but only the `Self` annotation lets `uvx mypy --strict` and `uvx pyright` both confirm `k.to_kelvin()` is valid without a manual cast.

## `@staticmethod` — utility functions

A static method receives **neither** the instance nor the class.
Use it for utilities that logically belong to the class but do not need access to class or instance state:

```python
    @staticmethod
    def absolute_zero() -> float:
        return -273.15
```

```python
print(Temperature.absolute_zero())   # -273.15
```

<Callout title="Prefer @property over getX/setX methods">
Java and older Python code uses explicit getter/setter methods like `get_celsius()` and `set_celsius(value)`.
In Python, `@property` gives you validation and computed values while keeping the call site looking like plain attribute access: `t.celsius = 0` instead of `t.set_celsius(0)`.
Start with a plain attribute; promote it to a `@property` later if you need validation or lazy computation — callers never need to change their code.
`@property` is itself a descriptor, so once you outgrow it — validation shared across many classes, or a computed value you want cached — writing your own descriptor or reaching for `cached_property` is a small step, not a new mental model.
</Callout>

## Mental Model

<Mermaid code={`flowchart TD

`@property`, `cached_property`, `classmethod`, `staticmethod`, and even a plain function stored on a class are all descriptors — the mechanism the classes lesson's attribute-lookup Mental Model glossed over as "class `__dict__`". A **data descriptor** (defines both `__get__` and `__set__`, like `property`) takes priority over the instance's own `__dict__` — that's why a computed `@property` can't be shadowed by `obj.attr = x` the way a plain class attribute can. A **non-data descriptor** (only `__get__`, like `cached_property` before its first access, or a plain method) loses to an instance `__dict__` entry with the same name — which is exactly how `cached_property` "caches": after the first access it writes an entry into `obj.__dict__`, and every later lookup finds that entry before the descriptor ever runs again.

## Trade-offs

| What you get | Benefit | Cost |
|---|---|---|
| `@property` | Validation and computed values behind plain-attribute syntax | Recomputes on every access |
| Custom descriptor | Reusable validation/logic shared across many classes and attributes | More boilerplate than a single `@property`; the protocol (`__get__`/`__set__`/`__set_name__`) has to be learned once |
| `@cached_property` | Computed once, then as fast as a normal attribute | Requires an instance `__dict__` (not compatible with `slots=True` unless the name is a slot); stale cache if the underlying data changes |
| `@classmethod` + `Self` | Alternative constructors that work correctly for subclasses | Returning the wrong literal type annotation (`"Temperature"` instead of `Self`) silently breaks subclass type-checking |
| `@staticmethod` | Groups a utility function under the class namespace | No access to `self` or `cls` — indistinguishable from a module-level function except for the namespace |

## Common Misconceptions

- **`@property` is special interpreter syntax, unrelated to normal classes.** It's an ordinary built-in class implementing the descriptor protocol (`__get__`/`__set__`) — you can write your own version in about ten lines.
- **A property without a setter can still be assigned, just without validation.** It can't be assigned at all — attempting `obj.attr = x` on a read-only property raises `AttributeError`, not a silent no-op.
- **`cached_property` re-runs its function every time, just faster.** It runs exactly once — the first access writes the value into the instance `__dict__`, and every access after that is a normal dict lookup that never calls the function again.
- **Annotating a classmethod's return type as the literal class name (`-> "Temperature"`) is just as correct as `Self`.** A type checker takes the literal name at face value even when `cls` is a subclass, producing false `attr-defined` errors on subclass-only methods; `Self` tracks the actual calling class.
- **`@staticmethod` and a module-level function are meaningfully different at runtime.** They behave the same when called — the only difference is namespacing (`ClassName.util()` vs a free function) and discoverability.

## Reading AI-generated code

Before trusting generated properties and class methods, check for:

- A `@classmethod` alternative constructor annotated `-> "ClassName"` (a string / forward reference to the literal class) instead of `-> Self` — this silently breaks type-checking the moment someone subclasses it.
- A `@cached_property` on a class with `slots=True` and no slot named for the cached attribute — this raises `AttributeError: 'ClassName' object has no attribute '__dict__'` at first access, since there's nowhere to store the cached value.
- Business logic or side effects (network calls, mutation of unrelated state) hidden inside a `@property` getter — a caller reading `obj.attr` has no syntactic hint that it might be slow or fail.
- A hand-written descriptor's `__get__` that doesn't handle `obj is None` (the case where the descriptor is accessed on the class itself, e.g. `Thermostat.celsius`) — it should return `self` (or a similar sentinel) rather than crashing.
- A `@staticmethod` that references `self` or `cls` at all — that's a sign it should be an instance or class method instead.
