## What are dunder methods?

**Dunder methods** (short for *double-underscore*) are special methods like `__repr__`, `__eq__`, and `__add__` that Python calls automatically in response to built-in syntax and functions.
They are the mechanism behind the **Python Data Model** — the contract that lets your objects behave like built-in types.

## `__repr__` and `__str__` — who calls which

Both produce string representations, but they serve different audiences:

| Method | When called | Purpose |
|---|---|---|
| `__repr__` | `repr(obj)`, interactive shell, **elements inside a container** | Unambiguous developer representation |
| `__str__` | `str(obj)`, `print(obj)`, f-string `{obj}` | Human-friendly display |

If only `__repr__` is defined, Python uses it for both.
The convention for `__repr__` is to return a string that, if passed to `eval()`, would recreate the object.

```python
class Point:
    def __init__(self, x: float, y: float) -> None:
        self.x = x
        self.y = y

    def __repr__(self) -> str:
        return f"Point({self.x}, {self.y})"

    def __str__(self) -> str:
        return f"({self.x}, {self.y})"
```

A detail that surprises people who define both: `print([Point(1, 2)])` prints `[Point(1, 2)]`, **not** `[(1, 2)]`. A list never calls `__str__` on its elements — it always calls `__repr__`, even though `print()` on the list itself uses the list's own `__str__` (which for a list *is* built from each element's `repr`). `__str__` is only reached when you convert or print the object *directly*.

## `__eq__` — equality

Python calls `__eq__` when you write `a == b`.
Without it, `==` falls back to identity comparison (`is`) — two separate instances with the same data are never equal.

```python
def __eq__(self, other: object) -> bool:
    if not isinstance(other, Point):
        return NotImplemented
    return self.x == other.x and self.y == other.y
```

## `__eq__` sets `__hash__` to `None` — the real `TypeError`, and two fixes

Defining `__eq__` on a class disables the default `__hash__` it inherited from `object` — Python sets `__hash__ = None` automatically, because two objects that compare equal must hash equal, and your custom `__eq__` broke that guarantee the interpreter could previously assume. The instance is now **unhashable**:

```python
class User:
    def __init__(self, uid: int) -> None:
        self.uid = uid

    def __eq__(self, other: object) -> bool:
        return isinstance(other, User) and self.uid == other.uid

cache = {}
cache[User(1)] = "active"
```

Run on 3.14, this raises `TypeError: cannot use 'User' as a dict key (unhashable type: 'User')` — and `hash(User(1))` directly raises `TypeError: unhashable type: 'User'`. Two fixes:

1. **Define `__hash__` yourself**, built from the same fields `__eq__` compares: `def __hash__(self) -> int: return hash(self.uid)`.
2. **Use a frozen dataclass** (`@dataclass(frozen=True)`) — it generates both a correct `__eq__` and a matching `__hash__` for you, as long as every field is itself hashable.

Either fix restores `hash(obj)` and lets instances live in sets and as dict keys again.

## `NotImplemented` and reflected operators

`NotImplemented` is a special singleton — not an exception — that a dunder method returns to say "I don't know how to do this with that other type; ask someone else." Python then tries the **reflected** method (`__radd__` for `+`, `__req__`-style for other operators) on the *other* operand. If every candidate returns `NotImplemented`, Python falls back to a default (`==` and `!=` fall back to identity; other operators raise `TypeError`).

```python
def __radd__(self, other: object) -> "Vector":
    # supports sum([...]), which starts by computing 0 + first_item
    if other == 0:
        return self
    return NotImplemented
```

Mixing this up with `NotImplementedError` (a real exception, meant for abstract methods) is a common bug: `Good(1) == "not a Good"` returns `False` because `NotImplemented` triggers Python's normal fallback, but a class that `raise NotImplementedError` from `__eq__` instead makes the *entire comparison* explode — `Bad(1) == "not a Bad"` raises `NotImplementedError: cannot compare` instead of quietly returning `False`. Verified on 3.14: both behaviors are exactly as described.

## `__len__` and `__getitem__`

Implement `__len__` to support `len(obj)`.
Implement `__getitem__` to support `obj[index]` subscript access.

```python
def __len__(self) -> int:
    return 2

def __getitem__(self, index: int) -> float:
    return (self.x, self.y)[index]
```

## `__iter__`/`__next__` vs the `__getitem__` fallback

The real iterator protocol is two methods: `__iter__` returns an iterator (often `self`), and `__next__` returns the next value or raises `StopIteration` to signal the end:

```python
class Countdown:
    def __iter__(self) -> "Countdown":
        self.current = self.start
        return self

    def __next__(self) -> int:
        if self.current <= 0:
            raise StopIteration
        self.current -= 1
        return self.current + 1
```

`__getitem__` alone is also enough to make an object iterable, through a **separate, legacy fallback**: if a class has no `__iter__`, Python's `for` loop calls `__getitem__` with `0, 1, 2, ...` until it raises `IndexError`, and stops there — `__len__` is not involved in that fallback at all. `list(LegacySequence([10, 20, 30]))` runs fine and prints `[10, 20, 30]` on CPython. But **both `uvx mypy --strict` and `uvx pyright` reject it** — they only model the modern `Iterable` protocol (`__iter__`), not the legacy `__getitem__` fallback: mypy reports `No overload variant of "list" matches argument type "LegacySequence"  [call-overload]`, and pyright reports `"LegacySequence" is incompatible with protocol "Iterable[_T@list]" — "__iter__" is not present`. This is a real gap between what CPython runs and what today's type checkers understand — prefer `__iter__`/`__next__` for anything you want a type checker to accept.

## `__len__`, `__bool__`, `__contains__`

```python
def __len__(self) -> int:
    return len(self.items)

def __bool__(self) -> bool:
    return len(self.items) > 0

def __contains__(self, item: object) -> bool:
    return item in self.items
```

`bool(obj)` calls `__bool__` if defined; without it, Python falls back to `__len__` (a length of `0` is falsy). `in` calls `__contains__` if defined; without it, `in` falls back to iterating with `__iter__`/`__getitem__`.

## `__call__` — making instances callable

Defining `__call__` lets you call an instance like a function — `obj(...)` becomes `obj.__call__(...)`:

```python
class Multiplier:
    def __init__(self, factor: int) -> None:
        self.factor = factor

    def __call__(self, value: int) -> int:
        return value * self.factor

double = Multiplier(2)
double(21)          # 42
callable(double)    # True
```

This is how decorators-as-classes and configurable callbacks work — the object carries state (`factor`) that a plain function couldn't hold without a closure.

## `__getattr__` vs `__getattribute__`

`__getattribute__` runs for **every** attribute access on the instance, found or not — overriding it is rare and easy to get wrong (infinite recursion if it calls `self.name` instead of `object.__getattribute__(self, name)`). `__getattr__` is the safer hook: it runs **only when normal lookup already failed** (instance `__dict__` and the class's MRO both missed), making it ideal for computed fallbacks or friendlier errors.

```python
def __getattr__(self, name: str) -> str:
    # only called when normal attribute lookup FAILS
    return f"<no setting {name!r}>"
```

`cfg.loaded` (a real attribute) never reaches `__getattr__` at all; `cfg.missing_setting` does, because normal lookup fails first.

## `__del__` is not reliable

`__del__` runs when an object's reference count hits zero — for a simple, cycle-free object under CPython, that happens right when the last reference is deleted, so it looks deterministic. It stops looking deterministic the moment two objects reference each other in a cycle: reference counting alone can never bring a cycle's count to zero, so `__del__` doesn't run until the *cyclic garbage collector* (`gc.collect()`, or its automatic periodic run) breaks the cycle — which can be much later, or, in the worst case (an exception during interpreter shutdown, or `gc` disabled), never. Verified: deleting two nodes that reference each other prints nothing until `gc.collect()` runs; a cycle-free object's `__del__` prints immediately on `del`. Never rely on `__del__` to release an external resource (a file, a socket, a lock) — use a context manager (`__enter__`/`__exit__`) instead.

## `functools.total_ordering`

Implementing every comparison operator (`__lt__`, `__le__`, `__gt__`, `__ge__`) by hand is repetitive. `@total_ordering` fills in the rest from just `__eq__` and *one* of the others:

```python
from functools import total_ordering

@total_ordering
class Money:
    def __eq__(self, other: object) -> bool:
        ...
    def __lt__(self, other: "Money") -> bool:
        return self.cents < other.cents
```

`sorted(prices)` and `Money(100) <= Money(200)` both work — `<=` was never written by hand; `total_ordering` derived it from `__eq__` and `__lt__`.

## Operator overloading with `__add__`

Arithmetic operators map to dunder methods:

| Operator | Method |
|---|---|
| `a + b` | `a.__add__(b)` |
| `a - b` | `a.__sub__(b)` |
| `a * b` | `a.__mul__(b)` |
| `a == b` | `a.__eq__(b)` |
| `a < b` | `a.__lt__(b)` |

```python
def __add__(self, other: "Vector") -> "Vector":
    return Vector(self.x + other.x, self.y + other.y)
```

## Mental Model

<Mermaid code={`flowchart TD
  A["a + b"] --> B{"a.__add__(b) returns NotImplemented?"}
  B -->|"no"| R1["use a.__add__(b)'s result"]
  B -->|"yes"| C{"b.__radd__(a) exists and returns NotImplemented?"}
  C -->|"no"| R2["use b.__radd__(a)'s result"]
  C -->|"yes"| E["TypeError: unsupported operand type(s)"]`} title="NotImplemented drives Python's operator dispatch, left operand first" />

Every piece of built-in syntax is really a lookup-and-call: `a + b` is `type(a).__add__(a, b)`, tried first; only if that returns `NotImplemented` does Python try `type(b).__radd__(b, a)`. The same shape — "try the direct dunder, fall back to a related one, only then give up" — reappears everywhere in this lesson: `bool(x)` tries `__bool__` then falls back to `__len__`; `for` tries `__iter__`/`__next__` then falls back to the `__getitem__` protocol; attribute access tries normal lookup then falls back to `__getattr__`. Reading a dunder-heavy class means asking, for each piece of syntax: which method runs first, and what does Python do if it opts out?

## Trade-offs

| What you get | Benefit | Cost |
|---|---|---|
| Custom `__eq__` | Value-based equality instead of identity | Disables `__hash__` — you must add it back by hand if you need hashing |
| `__iter__`/`__next__` | Real iterator protocol, understood by type checkers | Two methods instead of one |
| `__getitem__`-only iteration | Works with a single method, useful for existing indexable data | Not recognized as `Iterable` by mypy/pyright; only integer-indexed, `IndexError`-terminated data qualifies |
| `__call__` | Instances behave like functions and carry state | Easy to overuse where a plain function or method would read more clearly |
| `__getattr__` | Clean fallback for missing/computed attributes | Silently answering for typo'd attribute names can hide real bugs |
| `@total_ordering` | Write 2 comparisons, get all 4 | Slightly slower than hand-written operators (an extra function call per comparison) |

## Common Misconceptions

- **`__str__` is used everywhere `__repr__` isn't.** Containers (lists, dicts, tuples) always use `__repr__` for their elements — `print([obj])` never calls `obj.__str__()`.
- **Any class with `__eq__` can be put in a set or used as a dict key, same as before.** Defining `__eq__` sets `__hash__` to `None` unless you also define `__hash__` — the class becomes unhashable, with a `TypeError` at the point of use, not at definition time.
- **Returning `False` and raising `NotImplementedError` from `__eq__` are similarly "safe" ways to say no.** `NotImplemented` (no parentheses, not an exception) lets Python try the other operand and fall back gracefully; `NotImplementedError` is a real exception that blows up the whole comparison.
- **`__len__` is required for a `for` loop to work.** It is not involved in iteration at all — `__iter__`/`__next__`, or the `__getitem__` fallback, are what `for` actually uses.
- **`__del__` is a reliable place to release resources, like a destructor in C++.** It only runs promptly for cycle-free objects under CPython's refcounting; a reference cycle delays it until the cyclic GC runs, and it may never run before interpreter shutdown in edge cases. Use a context manager instead.

## Reading AI-generated code

Before trusting a generated class full of dunders, check for:

- Is `__eq__` defined without a matching `__hash__`? The class silently becomes unhashable — fine until someone puts an instance in a set or dict key, where it raises `TypeError` far from where `__eq__` was written.
- Does a comparison dunder `raise NotImplementedError` instead of `return NotImplemented`? That turns "try the other operand" into a crash.
- Is `__getitem__` used as the *only* iteration mechanism in code that will also be type-checked? `mypy --strict`/`pyright` reject passing such an object to `list(...)` or any `Iterable[...]` parameter, even though it runs on CPython.
- Does `__getattribute__` (not `__getattr__`) get overridden without ending in `object.__getattribute__(self, name)`? Calling `self.name` or `getattr(self, name)` instead recurses infinitely.
- Does cleanup logic (closing a file, releasing a lock) live only in `__del__`? That resource may stay open far longer than intended, or never close in a cycle.
