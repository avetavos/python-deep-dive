## Python's design philosophy

Python was designed around a single guiding principle: code should read like plain English.
Guido van Rossum, Python's creator, made explicit trade-offs in favour of readability — even when that meant restricting programmer freedom.

The philosophy is captured in **PEP 20**, known as *The Zen of Python*.
Run `import this` in any Python session to see it.
Three lines that shape everything:

- *Beautiful is better than ugly.*
- *Explicit is better than implicit.*
- *There should be one — and preferably only one — obvious way to do it.*

That last point matters most for learning: when you look up how to do something in Python, there is almost always a canonical answer.

## Significant whitespace

Python uses **indentation** (4 spaces per level, by convention) to define blocks.
There are no curly braces and no semicolons.

```python
def is_even(n: int) -> bool:
    if n % 2 == 0:
        return True
    return False

for i in range(5):
    if is_even(i):
        print(i, "is even")
```

Mixing tabs and spaces causes a `TabError`.
The community standard (PEP 8) is **4 spaces** — configure your editor once and forget about it.

## The "everything is an object" thesis

This is the single idea the rest of the course keeps coming back to: in Python, *everything you can name is an object* — not just the things that look like data. A number, a function, a class, a module, and even a type itself all have an identity (`id()`), a type (`type()`), and a set of attributes:

```python
print(type(42))            # <class 'int'>
print((42).bit_length())   # 6 -- an int has methods, because it's an object
print(type(print))         # <class 'builtin_function_or_method'>
print(type(int))           # <class 'type'> -- int itself is an instance of type
print(type(type))          # <class 'type'> -- type is an instance of itself
```

`int` is not a special primitive keyword — it is an object of type `type` (a class), the same way `Dog` would be if you defined it yourself. `print` is not special syntax either — it is a callable object, retrievable, assignable to another name, and passable as an argument like any other value. This single fact is why almost every later lesson can be explained in terms of "what object does this name refer to, and what happens when you call a method or operator on it" — there is no separate rulebook for "primitives" versus "objects."

## Trade-offs

| What you get | Benefit | Cost |
|---|---|---|
| Uniform object model | One mental model covers numbers, functions, classes, and modules | No separate "fast path" for primitives — everything carries object overhead |
| `type()` reveals the exact class | Precise, unambiguous introspection | Comparing `type(x) == SomeClass` silently rejects legitimate subclasses |
| Readability-first philosophy (PEP 20) | A canonical, discoverable way to do most things | Occasionally trades raw performance or terseness for clarity |
| 4-space indentation as syntax | Forces consistently readable block structure across any codebase | Mixing tabs and spaces is a hard error (`TabError`), not just a style nit |

## Common Misconceptions

- **"Numbers, strings, and booleans are primitives; only custom classes are objects."** They are all objects — `type(42)` is `int`, a real class, and `(42).bit_length()` proves it has methods like any other object.
- **"`type(x) == SomeClass` is the same as `isinstance(x, SomeClass)`."** It is not — `type(x) == SomeClass` is `False` for any subclass instance, while `isinstance` respects the whole class hierarchy.
- **"Python's readability rules (PEP 8/PEP 20) are just style preferences with no real effect."** They shape what "looks right" enough that deviations are often exactly where bugs hide — a codebase that follows one obvious way to do things is easier to read for bugs, human or AI-generated.
- **"A function or a class isn't really a value the way a number is."** Both are objects that can be assigned to a variable, stored in a list, or passed as an argument — `type(print)` and `type(int)` prove neither is special syntax.

## Reading AI-generated code

- Does a type check use `type(x) == SomeClass` where `isinstance(x, SomeClass)` is actually intended? The first silently rejects valid subclasses.
- Does the code assume "primitives" (numbers, booleans, strings) behave differently from "real objects" — for example assuming they have no methods or can't be subclassed?
- Whenever a lesson from here on gives you a checklist, does the code under review actually get checked against it, or does the review stop at "does it run"?
- Is a function or class being treated as something other than an ordinary value — for example, never assigned to a variable or passed as an argument, when doing so would simplify the code?

<SpotTheBug code={`def is_valid_item(item):
    if type(item) == dict:
        return "id" in item
    return False`} lang="python">
`type(item) == dict` only accepts a value whose type is *exactly* `dict` — a perfectly reasonable `dict` subclass (for example one returned by a library, or `collections.UserDict`, or a developer's own `class Config(dict): ...`) fails this check even though it behaves like a dict in every way that matters here. `isinstance(item, dict)` checks the whole class hierarchy and accepts subclasses too. The fix: `if isinstance(item, dict): return "id" in item`.
</SpotTheBug>

<Callout title="Python is fully object-oriented">
Everything in Python is an object — integers, strings, functions, classes, and even modules.
This means every value has a type (`type(42)` returns `int`), a set of attributes, and a set of methods.
You never need to "box" a primitive into a wrapper class as you would in Java.
</Callout>
