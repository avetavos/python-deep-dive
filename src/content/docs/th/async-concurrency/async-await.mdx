## Sequential เทียบกับ concurrent await

จุดสำคัญในการเขียนโปรแกรม async คือความแตกต่างระหว่างการ await coroutines แบบ **sequential**
กับการ schedule ให้รันแบบ **concurrent**

การ await ทีละตัวคือ sequential — แต่ละ coroutine ต้องเสร็จก่อนตัวถัดไปจะเริ่ม:

```python
import asyncio

async def fetch(label: str, delay: float) -> str:
    await asyncio.sleep(delay)
    return f"{label} result"

async def sequential() -> None:
    a = await fetch("A", 0.3)   # waits 0.3 s
    b = await fetch("B", 0.2)   # waits 0.2 s after A finishes
    print(a, b)
    # Total: ~0.5 s

asyncio.run(sequential())
```

การใช้ `asyncio.gather` รันแบบ concurrent — เวลารวมเท่ากับตัวที่ช้าที่สุด ไม่ใช่ผลรวม:

```python
import asyncio

async def fetch(label: str, delay: float) -> str:
    await asyncio.sleep(delay)
    return f"{label} result"

async def concurrent() -> None:
    a, b = await asyncio.gather(
        fetch("A", 0.3),
        fetch("B", 0.2),
    )
    print(a, b)
    # Total: ~0.3 s

asyncio.run(concurrent())
```

## `asyncio.create_task` — schedule task อย่างชัดเจน

`asyncio.create_task(coro)` ห่อ coroutine ไว้ใน `Task` และ schedule บน event loop ที่กำลังรันทันที
ต่างจากการเรียก coroutine ตรงๆ task จะเริ่มรันทันทีที่ coroutine ปัจจุบันยกการควบคุม

```python
import asyncio

async def worker(name: str, delay: float) -> str:
    print(f"{name}: starting")
    await asyncio.sleep(delay)
    print(f"{name}: done")
    return f"{name}-result"

async def main() -> None:
    # Schedule both tasks immediately — they run concurrently
    task_a = asyncio.create_task(worker("A", 0.3))
    task_b = asyncio.create_task(worker("B", 0.1))

    # Await them to collect results
    result_a = await task_a
    result_b = await task_b
    print(result_a, result_b)

asyncio.run(main())
# A: starting
# B: starting
# B: done
# A: done
# A-result B-result
```

สังเกตว่า "B: done" ปรากฏก่อน "A: done" แม้เราจะ `await task_a` ก่อนก็ตาม —
tasks รันแบบ concurrent และ B เสร็จเร็วกว่า

## กับดัก fire-and-forget: เก็บ reference ของ task ไว้เสมอ

การเรียก `asyncio.create_task(coro)` โดยไม่เก็บผลลัพธ์ไว้มัก compile และรันได้ในตัวอย่างสั้นๆ — ซึ่งเป็นสิ่งที่ทำให้มันอันตราย เอกสารทางการพูดถึงความเสี่ยงนี้ตรงๆ: *"the event loop only keeps weak references to tasks. A task that isn't referenced elsewhere may get garbage collected at any time, even before it's done."* ไม่มีอะไรในภาษาบังคับให้คุณเก็บ reference ดังนั้นไม่มีอะไรเตือนตอนที่คุณลืม:

```python
import asyncio

async def background_job(label: str) -> None:
    await asyncio.sleep(0.05)
    print(f"{label}: finished")

async def fire_and_forget() -> None:
    asyncio.create_task(background_job("leaked"))   # no variable holds the Task
    await asyncio.sleep(0.1)   # only works because the loop's own scheduling keeps it alive here
```

การแก้ไม่มีต้นทุนและไม่มีข้อเสีย — เก็บ task ไว้ใน set แล้วให้ done-callback ทำความสะอาด set เมื่อเสร็จ:

```python
import asyncio

background_tasks: set[asyncio.Task] = set()

async def background_job(label: str) -> None:
    await asyncio.sleep(0.05)
    print(f"{label}: finished")

def spawn(coro) -> asyncio.Task:
    task = asyncio.create_task(coro)
    background_tasks.add(task)
    task.add_done_callback(background_tasks.discard)
    return task
```

หรือถ้า task แบบ fire-and-forget มี lifetime ร่วมกับ block ของโค้ด ให้ใช้ `TaskGroup` แทนการจดบันทึกเอง — มันทำให้ "รอทุกอย่างที่ฉันเริ่ม" เป็นค่า default แทนที่จะเป็นสิ่งที่ต้องจำเอง

## `TaskGroup` cancellation เทียบกับ `gather(return_exceptions=True)`

ทั้ง `TaskGroup` และ `gather(return_exceptions=True)` ให้คุณรัน coroutine หลายตัวและเห็นทุกผลลัพธ์แม้บางตัว fail — แต่ทั้งสองไม่เห็นตรงกันว่าเกิดอะไรกับ *ผู้รอดชีวิต*:

```python
import asyncio

async def worker(label: str, delay: float, fail: bool) -> str:
    await asyncio.sleep(delay)
    if fail:
        raise ValueError(f"{label} failed")
    return f"{label} ok"

async def main() -> None:
    results = await asyncio.gather(
        worker("A", 0.05, False),
        worker("B", 0.02, True),
        worker("C", 0.08, False),
        return_exceptions=True,
    )
    print(results)
    # ['A ok', ValueError('B failed'), 'C ok'] — C still ran to completion

asyncio.run(main())
```

```python
import asyncio

async def worker(label: str, delay: float, fail: bool) -> str:
    await asyncio.sleep(delay)
    if fail:
        raise ValueError(f"{label} failed")
    return f"{label} ok"

async def main() -> None:
    try:
        async with asyncio.TaskGroup() as tg:
            tg.create_task(worker("A", 0.05, False))
            tg.create_task(worker("B", 0.02, True))
            tg.create_task(worker("C", 0.08, False))
    except* ValueError as eg:
        print([str(e) for e in eg.exceptions])
        # ['B failed'] — B's failure cancelled C before its 0.08s sleep finished

asyncio.run(main())
```

`gather(return_exceptions=True)` ไม่ยกเลิกอะไรเลย — ทุก coroutine ที่ส่งเข้าไปรันจนจบไม่ว่าตัวอื่นจะเป็นอย่างไร แล้วคุณแยก success กับ exception เอง `TaskGroup` มองว่าความล้มเหลวหนึ่งครั้งเป็นเหตุให้ยกเลิกทั้งกลุ่ม: เป็นค่า default ที่ถูกต้องเมื่อ task ทำงานไปสู่เป้าหมายเดียวกัน (request fan-out ที่ผลลัพธ์บางส่วนไม่มีประโยชน์) และผิดเมื่อคุณต้องการทุกผลลัพธ์แบบอิสระจากความล้มเหลวของตัวอื่นจริงๆ (batch job ที่รายงานสถานะทีละรายการ)

## Timeouts: `asyncio.timeout()` และ `wait_for`

`asyncio.timeout()` (3.11+) เป็น context manager: ทุกอย่างข้างในถูกยกเลิกถ้า block ไม่เสร็จภายในเวลาที่กำหนด แล้ว raise `TimeoutError`

```python
import asyncio

async def slow_op() -> str:
    await asyncio.sleep(5)
    return "done"

async def main() -> None:
    try:
        async with asyncio.timeout(0.1):
            await slow_op()
    except TimeoutError:
        print("operation timed out")

asyncio.run(main())
# operation timed out
```

`asyncio.wait_for(coro, timeout)` คือรูปแบบเก่ากว่าที่ครอบ awaitable ตัวเดียว — ต่างจาก `timeout()` ที่ครอบ block ได้ ซึ่งสำคัญถ้าต้องการจำกัดเวลาหลาย statement พร้อมกัน (มีแค่ `timeout()` เท่านั้นที่ครอบมากกว่าหนึ่งบรรทัดได้) ทั้งสองยกเลิกแบบเดียวกันและ raise `TimeoutError` เหมือนกัน (ตั้งแต่ 3.11 `asyncio.TimeoutError` เป็น alias ของ builtin) `asyncio.shield(coro)` คือเครื่องมือตรงข้าม: มันปกป้อง awaitable จากการถูกยกเลิก *โดยผู้เรียก* — มีประโยชน์เมื่อขั้นตอน cleanup ต้องเสร็จแม้ operation รอบนอกจะถูกยกเลิก — แต่มันไม่ป้องกัน `timeout()`/`wait_for` ที่ครอบตัว shield เองจาก timeout; coroutine ข้างใน `shield` ยังถูกยกเลิกเองได้อิสระ

## Blocking call ทำให้ loop แข็ง — `time.sleep` เทียบกับ `asyncio.sleep`

`time.sleep()` block ทั้ง OS thread ที่ event loop รันอยู่ เมื่อเรียกจากภายใน coroutine มันไม่ได้ "หยุด task นั้น" แบบที่ `asyncio.sleep()` ทำ — มันหยุด *ทุกอย่าง* เพราะมีแค่เธรดเดียวที่รัน loop:

```python
import asyncio

async def heartbeat(n: int) -> None:
    for i in range(n):
        await asyncio.sleep(0.03)
        print(f"heartbeat {i}")

def blocking_sleep(seconds: float) -> str:
    import time
    time.sleep(seconds)      # blocks the WHOLE event loop thread
    return "worker done"

async def main() -> None:
    hb = asyncio.create_task(heartbeat(2))
    result = await asyncio.to_thread(blocking_sleep, 0.08)  # runs off the event loop's thread
    print(result)
    await hb

asyncio.run(main())
# heartbeat 0
# heartbeat 1
# worker done
```

`asyncio.to_thread(fn, *args)` (3.9+) คือทางแก้: มันรัน call ที่ block จริงๆ — `time.sleep`, synchronous DB driver, file I/O เบาๆ — ใน thread pool ทำให้ event loop ยังให้บริการ coroutine อื่นได้ระหว่างรอ มันเป็น wrapper บาง ๆ ของ `loop.run_in_executor(None, functools.partial(fn, *args))` ซึ่งอยู่ในบท GIL & Threads

## `Semaphore` — จำกัด concurrency

`asyncio.Semaphore(n)` ให้ coroutine ถือมันพร้อมกันได้สูงสุด `n` ตัว — วิธีมาตรฐานในการจำกัด request ที่ concurrent ไปยัง API ที่มี rate limit หรือ connection pool:

```python
import asyncio

async def limited_call(sem: asyncio.Semaphore, label: str, active: list) -> None:
    async with sem:
        active.append(label)
        print(f"{label}: running, concurrent={len(active)}")
        await asyncio.sleep(0.05)
        active.remove(label)

async def main() -> None:
    sem = asyncio.Semaphore(2)
    active: list = []
    await asyncio.gather(*[limited_call(sem, f"job-{i}", active) for i in range(4)])

asyncio.run(main())
# never more than 2 "running" lines are concurrent
```

## `Queue` — producer/consumer

`asyncio.Queue` คือเทียบเท่าแบบ async-native ของ `queue.Queue`: `put`/`get` เป็น coroutines ดังนั้น queue ที่เต็มจะหยุด producer (แทนที่จะ block thread) จนกว่า consumer จะดึงออกไป

```python
import asyncio

async def producer(q: asyncio.Queue, n: int) -> None:
    for i in range(n):
        await q.put(i)
    await q.put(None)   # sentinel signals "no more items"

async def consumer(q: asyncio.Queue, out: list) -> None:
    while True:
        item = await q.get()
        if item is None:
            break
        out.append(item)

async def main() -> None:
    q: asyncio.Queue = asyncio.Queue(maxsize=2)   # bounded — producer waits if it fills up
    out: list = []
    await asyncio.gather(producer(q, 4), consumer(q, out))
    print(out)   # [0, 1, 2, 3]

asyncio.run(main())
```

## `Lock` — check-then-act ยังเป็น race ข้าม `await`

Event loop เธรดเดียวหมายความว่าไม่มี coroutine สองตัวรัน bytecode ในเสี้ยววินาทีเดียวกัน — แต่นั่น **ไม่ได้** แปลว่า shared state ปลอดภัย `await` ใดๆ ระหว่าง check กับ action ที่มัน guard คือช่องว่างที่ coroutine อื่นวิ่งเข้ามาเปลี่ยน state ก่อนได้:

```python
import asyncio

class Account:
    def __init__(self, balance: int) -> None:
        self.balance = balance

async def withdraw_unsafe(acct: Account, amount: int) -> None:
    if acct.balance >= amount:   # check
        await asyncio.sleep(0)   # <-- another coroutine can run right here
        acct.balance -= amount   # act -- based on a now-stale read

async def main() -> None:
    acct = Account(balance=100)
    await asyncio.gather(withdraw_unsafe(acct, 80), withdraw_unsafe(acct, 80))
    print(acct.balance)   # -60 -- both checks passed before either write happened

asyncio.run(main())
```

`asyncio.Lock` ปิดช่องว่างนี้โดยทำให้ check-and-act เป็นหน่วยเดียวที่ทำต่อเนื่อง:

```python
import asyncio

class Account:
    def __init__(self, balance: int) -> None:
        self.balance = balance
        self.lock = asyncio.Lock()

async def withdraw_safe(acct: Account, amount: int) -> None:
    async with acct.lock:
        if acct.balance >= amount:
            await asyncio.sleep(0)
            acct.balance -= amount

async def main() -> None:
    acct = Account(balance=100)
    await asyncio.gather(withdraw_safe(acct, 80), withdraw_safe(acct, 80))
    print(acct.balance)   # 20 -- the second withdrawal correctly sees the updated balance

asyncio.run(main())
```

นี่คือความจริงในโลก async ของสิ่งที่จริงกับ thread เช่นกัน: **ไม่มี data race (undefined behavior) ไม่ได้แปลว่าไม่มี race condition** Event loop เธรดเดียวรับประกันว่าคุณจะไม่ทำ memory เสียหายจาก coroutine สองตัวเขียนพร้อมกัน — แต่มันไม่รับประกันความถูกต้องเชิง*ตรรกะ*ของลำดับ check-then-act ที่คร่อม `await` เลย `asyncio.Event` คือ primitive คู่กันในทิศตรงข้าม — ไม่ใช่ "ทีละตัว" แต่เป็น "ทุกคนรอจนกว่าฉันจะบอกให้ไป": `await event.wait()` หยุดจนกว่า coroutine อื่นจะเรียก `event.set()`

## Pattern ที่ใช้จริง: retry, rate limiting และ graceful shutdown

**Retry แบบ exponential backoff และ jitter** — การ retry ทันทีหลัง transient failure มักแค่ทำให้ failure เกิดซ้ำ (หรือไปโดน server ที่ overload อยู่แล้ว); backoff เว้นระยะ retry ออกจากกัน และ jitter (สุ่มระยะเวลา) ป้องกันไม่ให้ client หลายตัว retry พร้อมกันเป็นจังหวะเดียวกัน:

```python
import asyncio
import random

class FlakyError(Exception):
    pass

async def retry_with_backoff(coro_fn, *, max_attempts: int = 5, base: float = 0.01) -> object:
    for attempt in range(1, max_attempts + 1):
        try:
            return await coro_fn()
        except FlakyError:
            if attempt == max_attempts:
                raise
            delay = base * (2 ** (attempt - 1)) + random.uniform(0, base)
            await asyncio.sleep(delay)
```

**Rate limiting** — token bucket จำกัดว่า action หนึ่งเกิดขึ้นได้บ่อยแค่ไหน ไม่ขึ้นกับจำนวนผู้เรียกที่รออยู่:

```python
import asyncio

class RateLimiter:
    def __init__(self, rate: int, period: float) -> None:
        self.rate = rate
        self.period = period
        self.tokens = float(rate)

    async def acquire(self) -> None:
        while self.tokens < 1:
            await asyncio.sleep(self.period / self.rate)
            self.tokens += 1
        self.tokens -= 1
```

**Graceful shutdown** — service ที่รันยาวควรหยุดรับงานใหม่และปล่อยให้งานที่กำลังทำอยู่เสร็จ (หรือยกเลิกอย่างตั้งใจ) เมื่อถูกขอให้หยุด แทนที่จะถูก kill กลาง request รูปแบบทั่วไปคือ shutdown `asyncio.Event` ที่ set จาก signal handler โดย worker loop คอยเช็ค:

```python
import asyncio
import signal

async def worker(shutdown: asyncio.Event) -> None:
    while not shutdown.is_set():
        await asyncio.sleep(0.1)   # do one unit of work per iteration in a real service
    print("worker exiting cleanly")

async def main() -> None:
    shutdown = asyncio.Event()
    loop = asyncio.get_running_loop()
    loop.add_signal_handler(signal.SIGTERM, shutdown.set)   # Unix only; not testable on Pyodide
    async with asyncio.TaskGroup() as tg:
        tg.create_task(worker(shutdown))
        # ... other tasks ...
```

`loop.add_signal_handler` ใช้ได้เฉพาะ Unix และต้องมี OS signal จริงเพื่อสาธิต จึงไม่รวมอยู่ใน demo ที่รันได้ด้านล่าง — pattern (`Event`, worker คอยเช็ค, `TaskGroup` เพื่อให้ shutdown รอทุก worker) เหมือนกันไม่ว่าตัวกระตุ้นจะเป็น signal หรืออย่างใน demo คือ coroutine อื่นเรียก `shutdown.set()`

### Structured concurrency

แนวคิดหลักของ `TaskGroup` — ทุก task ที่คุณ spawn มีเจ้าของชัดเจน และเจ้าของนั้นออกไม่ได้จนกว่า child ทั้งหมดจะเสร็จหรือถูกยกเลิก — เรียกว่า **structured concurrency** มันตัด bug ทั้งกลุ่มที่โค้ดแบบ `create_task`-แล้วลืมชักชวนให้เกิด: task ที่มีอายุยืนกว่า scope ที่ควรเป็นเจ้าของมัน, exception ใน child ที่ไม่มีใครสังเกตเห็น, โปรแกรมออกไปทั้งที่งาน background ยังทำอยู่ `gather` และ `create_task` เปล่าๆ ไม่บังคับสิ่งนี้ แต่ `TaskGroup` บังคับ

### นอกเหนือจาก standard library

`asyncio` เป็น async framework ในตัวเดียวของ CPython แต่ third-party library สองตัวควรรู้จักไว้แม้จะรันใน Pyodide sandbox ของคอร์สนี้ไม่ได้: **anyio** ให้ API เดียวที่รันบน event loop ของ `asyncio` หรือ `trio` ก็ได้ มีประโยชน์สำหรับโค้ด library ที่ไม่ควรบังคับตัวเลือกให้ผู้เรียก; **trio** เป็นผู้บุกเบิกโมเดล structured-concurrency ที่ `TaskGroup` เอามาใช้ใน `asyncio` เองในภายหลัง สำหรับ HTTP โดยเฉพาะ `httpx.AsyncClient` คือคู่แบบ async-native ของ `requests` — การเรียก `requests.get()` แบบ synchronous ภายใน coroutine จะ block loop เหมือน `time.sleep` ด้านบนทุกประการ

## Nested `asyncio.run` raise `RuntimeError`

การเรียก `asyncio.run` สองครั้งติดกันที่ระดับบนสุดทำได้ปกติ (ดูบท asyncio พื้นฐาน) แต่การเรียก **จากภายใน** coroutine ที่กำลังรันบน loop อยู่แล้วไม่ได้ — มี loop รันอยู่ในเธรดนี้แล้ว และ `asyncio.run` ปฏิเสธที่จะเริ่มตัวที่สอง:

```python
import asyncio

async def inner() -> None:
    print("inner")
```

## ข้อแลกเปลี่ยน

| สิ่งที่ได้ | ประโยชน์ | ต้นทุน |
|---|---|---|
| `create_task` (เปล่าๆ) | เริ่มงานทันที พิธีกรรมน้อย | ไม่มีอะไรบังคับให้เก็บ reference — ถูกเก็บกวาดแบบเงียบๆ ได้ |
| `TaskGroup` | lifetime มีโครงสร้าง failure หนึ่งยกเลิกที่เหลือ | all-or-nothing; batch ที่ต้องการ partial success ต้องใช้ `gather` แทน |
| `gather(return_exceptions=True)` | ทุก task รันจนจบไม่ว่าตัวอื่นจะ fail | ต้องเช็ค `isinstance(r, Exception)` เองทุกผลลัพธ์ |
| `Semaphore` / rate limiting | ปกป้อง service หรือ pool ปลายทางจาก overload | เพิ่ม latency ให้ผู้เรียกเมื่อถึง limit |
| `asyncio.to_thread` | blocking call ไม่ทำให้ loop แข็งอีกต่อไป | overhead ของ thread pool; งาน pure-Python ยังโดน GIL |
| Retry แบบ backoff + jitter | รอด transient failure โดยไม่ยิง server ที่กำลังแย่ซ้ำๆ | บัง dependency ที่พังถาวรไว้จนครบ `max_attempts` ครั้งก่อน |

## ความเข้าใจผิดที่พบบ่อย

- **"`create_task` กับ `await coro` ใช้แทนกันได้"** `create_task` schedule ทันทีแล้วคืนการควบคุมทันที; `await coro` เปล่าๆ รัน (และ block บน) coroutine ตัวนั้นก่อนไปต่อ สลับสองอย่างนี้คือวิธีที่ fan-out แบบ "concurrent" กลายเป็น sequential แบบเงียบๆ
- **"task ที่ไม่มีตัวแปรชี้ถึงจะถูก garbage collect แน่นอน"** ปกติ loop เองมักเก็บมันไว้ให้เสร็จได้ในตัวอย่างสั้นๆ — ซึ่งนี่แหละที่ทำให้ bug นี้พลาดง่ายตอน code review และไม่แน่นอนเมื่อพยายาม reproduce คำแนะนำอย่างเป็นทางการให้เก็บ reference มีอยู่ไม่ว่า run ไหนจะแสดงปัญหาหรือไม่
- **"`gather(return_exceptions=True)` กับ `TaskGroup` เป็นแค่การเขียนสองแบบของสิ่งเดียวกัน"** ทั้งสองต่างกันโดยตั้งใจ: `gather` ไม่เคยยกเลิก sibling; `TaskGroup` ยกเลิกเสมอเมื่อ fail ครั้งแรก
- **"event loop เธรดเดียวหมายความว่า shared state ไม่ต้องใช้ lock เลย"** ไม่มี coroutine สองตัวรัน bytecode ในเสี้ยววินาทีเดียวกันจริง แต่ลำดับ check-then-act ที่คร่อม `await` ยังเป็น race — check อาจเก่าไปแล้วตอนที่ action รัน
- **"`asyncio.shield` ทำให้ coroutine ยกเลิกไม่ได้"** มันปกป้องแค่จาก cancellation ที่*แพร่มาจากการยกเลิกของผู้เรียก*; coroutine ที่ shield ยังถูกยกเลิกเองได้ และ `timeout()`/`wait_for` ที่ครอบ shield ยังมีผล

## อ่านโค้ดที่ AI เขียน

ก่อนเชื่อโค้ด task/concurrency ที่ AI สร้าง ตรวจสิ่งเหล่านี้:

- ทุก `asyncio.create_task(...)` เก็บผลลัพธ์ไว้ในสิ่งที่มีอายุยืนกว่า statement ปัจจุบันหรือไม่ (ตัวแปร, set, `TaskGroup`)? `asyncio.create_task(coro())` เปล่าๆ บนบรรทัดของตัวเองคือ fire-and-forget task ที่ไม่มีอะไรติดตาม
- ใช้ `gather` ในจุดที่ task ทำงานไปสู่เป้าหมายร่วมกันจริงๆ หรือไม่ (ควรเป็น `TaskGroup` ให้ failure หนึ่งยกเลิกที่เหลือหรือเปล่า)?
- มี shared object ที่ถูกอ่านแล้วแก้ไข โดยมี `await` คั่นกลาง โดยไม่มี `Lock` ครอบทั้งลำดับหรือไม่?
- มี blocking call จริงๆ (`time.sleep`, `requests.get` แบบ synchronous, งาน CPU หนัก) อยู่ตรงๆ ใน `async def` แทนที่จะอยู่หลัง `asyncio.to_thread` หรือ `run_in_executor` หรือไม่?
- retry loop retry ไม่มีที่สิ้นสุดโดยไม่มี `max_attempts` หรือ retry ด้วย delay คงที่ที่อาจทำให้ client หลายตัว sync กันยิง server ที่กำลังแย่พร้อมกัน (ไม่มี jitter) หรือไม่?
