## Mutability

### 1. Mutable default argument ถูกสร้างครั้งเดียว ไม่ใช่ทุก call

`cart: list[str] = []` ถูก evaluate ครั้งเดียวเป๊ะ ตอนที่ `add_item` ถูก *define* — ไม่ใช่ครั้งละ call ทุก call ที่ไม่ได้ส่ง `cart` ของตัวเองมาจะแชร์ list object เดียวกันนั้นตลอดไป

**อาการ — output จริง** (ตรงกับ playground ด้านบน):

```text
['apple', 'banana']
True
```

`second = add_item("banana")` ควรจะเริ่ม cart ใหม่ แต่กลับไป append ต่อบน cart ของ call *แรก* และ `second is first` พิสูจน์ว่ามันเป็น object เดียวกัน

**ทางแก้:** ใช้ default เป็น `None` แล้วสร้าง list ข้างใน function body:

```python
def add_item(item: str, cart: list[str] | None = None) -> list[str]:
    if cart is None:
        cart = []
    cart.append(item)
    return cart
```

**Caught by:** `ruff`'s `B006` ตรง ๆ ไม่ต้องตั้งค่าอะไรเพิ่ม:

```text
B006 Do not use mutable data structures for argument defaults
help: Replace with `None`; initialize within function
```

### 2. Closure ใน loop capture ตัวแปร loop ไม่ใช่ค่าของมัน

```python
def make_multipliers() -> list:
    return [lambda x: x * i for i in range(3)]


fns = make_multipliers()
print([f(10) for f in fns])
```

แต่ละ lambda close over *ตัวแปร* `i` ไม่ใช่ค่าที่มันมีตอน lambda ถูกสร้าง พอถึงเวลาเรียก lambda ตัวไหนก็ตาม comprehension ทำงานเสร็จไปแล้ว และ `i` มีค่าสุดท้าย คือ `2` — ทุก lambda เห็น `i` ตัวสุดท้ายเดียวกัน

**อาการ — output จริง:**

```text
[20, 20, 20]
```

ไม่ใช่ `[0, 10, 20]` ซึ่งเป็นสิ่งที่ผู้อ่านที่อ่านผ่าน ๆ "แต่ละ lambda คูณด้วย `i` ของตัวเอง" จะคาดหวัง

**ทางแก้:** bind ค่าปัจจุบันเป็น default argument ซึ่ง *ถูก* evaluate ครั้งเดียวตอนสร้าง lambda แต่ละตัว:

```python
def make_multipliers() -> list:
    return [lambda x, i=i: x * i for i in range(3)]
```

**Caught by:** `ruff`'s `B023` ตรง ๆ:

```text
B023 Function definition does not bind loop variable `i`
```

### 3. Aliasing — function mutate list ที่ผู้เรียกส่งเข้ามา

```python
def normalize(scores: list[int]) -> list[int]:
    scores.sort()
    for i in range(len(scores)):
        scores[i] = max(scores[i], 0)
    return scores


original = [3, -1, 2]
result = normalize(original)
print("caller's list after normalize:", original)
print("result is original:", result is original)
```

`normalize` ดูเหมือน pure function — รับ list แล้วคืน list — แต่ `scores.sort()` และ `scores[i] = ...` ทั้งคู่ mutate list object เอง `original` ของผู้เรียกเปลี่ยนไปทั้งที่ไม่มีอะไรตรงจุดที่เรียก (`normalize(original)`) บ่งบอกแบบนั้นเลย

**อาการ — output จริง:**

```text
caller's list after normalize: [0, 2, 3]
result is original: True
```

ผู้เรียกน่าจะคาดหวังว่า `original` จะยังเป็น `[3, -1, 2]` และ `result` เป็น copy ที่ normalize แล้ว

**ทางแก้:** copy ก่อน mutate ถ้า function ตั้งใจให้ non-destructive: `scores = list(scores)` เป็นบรรทัดแรก หรือใช้ `sorted(scores)` แทน `scores.sort()`

**Caught by:** ไม่มี นี่เป็นคำถามเชิง semantic/API-contract ล้วน ๆ — ไม่มี linter ตัวไหนนับว่า docstring หรือชื่อ function สัญญาไว้ว่าจะไม่ mutate argument ของมัน ดู **[Lists & Tuples](/python/th/data-structures/lists-tuples/)**

### 4. `[[0] * n] * m` — ทุกแถวคือ list เดียวกันที่แชร์กัน

```python
grid = [[0] * 3] * 3
grid[0][0] = 1
print(grid)
```

`[[0] * 3] * 3` สร้าง inner list *หนึ่งตัว* คือ `[0, 0, 0]` แล้วทำซ้ำ *reference* ไปยัง list ตัวเดียวกันนั้นสามครั้ง — ไม่ได้สร้างสามแถวที่เป็นอิสระต่อกัน

**อาการ — output จริง:**

```text
[[1, 0, 0], [1, 0, 0], [1, 0, 0]]
```

การเขียนไปที่ `grid[0][0]` เปลี่ยนทุกแถว เพราะทั้งสามแถวเป็น object เดียวกัน

**ทางแก้:** สร้างแต่ละแถวแยกกันด้วย comprehension เพื่อให้ `[0] * 3` แต่ละครั้งสร้าง list ใหม่:

```python
grid = [[0] * 3 for _ in range(3)]
```

**Caught by:** ไม่มี — ทั้งเวอร์ชันที่ผิดและที่แก้แล้วเป็น Python ปกติที่ valid ทั้งคู่ นี่เป็นกับดักเชิง semantic ล้วน ๆ ในวิธีที่ `*` บน list ทำซ้ำ reference ไม่ใช่ค่า ดู **[Lists & Tuples](/python/th/data-structures/lists-tuples/)**

## Errors

### 5. ใช้ `is` เทียบค่าแทนที่จะเป็น `==`

```python
a = "hello"
b = "".join(["h", "e", "l", "l", "o"])
print(a == b)
print(a is b)

x = 1000
y = int("1000")
print(x == y)
print(x is y)
```

`is` เช็ค object identity ไม่ใช่ equality CPython intern integer เล็ก ๆ บางตัว (`-5` ถึง `256`) และ string literal บางตัวที่ compile พร้อมกัน ซึ่งทำให้ `is` ดูเหมือน "ใช้ได้" สำหรับค่าในช่วงนั้น — แต่ `b` ถูกสร้างตอน runtime ผ่าน `.join()` และ `y` ผ่าน `int(str)` ดังนั้นทั้งคู่ไม่ใช่ object เดียวกันกับคู่ที่เทียบเท่ากันด้วย `==`

**อาการ — output จริง:**

```text
True
False
True
False
```

ทั้งสองคู่เท่ากัน (`==` เป็น `True`) แต่ไม่มีคู่ไหนเป็น *object เดียวกัน* (`is` เป็น `False`) — `is` ให้คำตอบผิดสำหรับ "ค่าเหล่านี้เหมือนกันไหม" ทันทีที่ operand ตัวใดตัวหนึ่งไม่ใช่ integer เล็ก ๆ ที่ถูก cache หรือ literal ที่ถูก deduplicate ตอน compile

**ทางแก้:** ใช้ `==` สำหรับเทียบค่า สงวน `is` ไว้สำหรับเช็ค singleton (`is None`, `is True`, `is False`) ที่ identity *คือ* contract จริง ๆ

**Caught by:** `ruff`'s `F632` แต่จับได้เฉพาะรูปแบบ literal ตรง ๆ (`x is 5`, `s is "foo"`):

```text
F632 Use `==` to compare constant literals
```

รูปแบบตัวแปรเทียบกับตัวแปรที่แสดงข้างบน — ตัวที่กัด demo นี้จริง ๆ — ไม่ถูกจับโดย `F632` หรือเครื่องมือไหนใน list ของคอร์สนี้เลย ความบังเอิญเรื่อง object identity ต้องจับด้วยตาเท่านั้น ดู **[Variables & Types](/python/th/basics/variables-types/)**

### 6. `except` ที่กว้างเกินไปกลืนสิ่งที่ผิดแบบเงียบ ๆ

```python
def risky_lookup(data: dict, key: str) -> int:
    try:
        return data[key]
    except:
        pass
    return -1


print(risky_lookup({}, "x"))
print(risky_lookup(None, "x"))
```

**อาการ — output จริง:**

```text
-1
-1
```

key ที่ไม่มีอยู่คืน `-1` ถูกต้อง แต่ `risky_lookup(None, "x")` raise `TypeError: 'NoneType' object is not subscriptable` — เป็น bug จริง (argument type ผิด) ไม่ใช่ key ที่หาย — และ bare `except:` กลืนมันแบบเดียวกันเป๊ะ คืน `-1` ราวกับไม่มีอะไรเกิดขึ้น

เวอร์ชัน async ของ bug นี้อันตรายกว่า: การจับกว้างเกินไปคาบเกี่ยว `await` สามารถกลืน cancellation ของ task เองได้

```python
async def worker(n: int) -> None:
    try:
        await asyncio.sleep(n)
        print(f"worker {n} finished normally")
    except BaseException as e:
        print(f"worker swallowed {type(e).__name__}: {e!r} -- keeps running")


async def main() -> None:
    task = asyncio.create_task(worker(5))
    await asyncio.sleep(0.05)
    task.cancel()
    await task
    print("main: task.cancelled() =", task.cancelled())
```

**อาการ — output จริง:**

```text
worker swallowed CancelledError: CancelledError() -- keeps running
main: task.cancelled() = False
```

`task.cancel()` ควรจะทำให้ task หยุด แต่ `except BaseException` กลับจับ `asyncio.CancelledError` ที่ raise ข้างใน `await asyncio.sleep(n)` พิมพ์ข้อความ แล้ว return ตามปกติ — `task.cancelled()` เป็น `False` แปลว่า cancellation request ถูกกลืนไปแบบเงียบ ๆ และ task รายงานตัวเองว่าจบตามปกติ

**ทางแก้:** ระบุ exception เฉพาะเจาะจงที่คาดไว้ (`except KeyError:` สำหรับ sync case) ใน async code ห้ามจับ `BaseException` (หรือ bare `except:`) คาบเกี่ยว `await` เว้นแต่จะ re-raise `asyncio.CancelledError` ทันที การจับแค่ `Exception` ปลอดภัยกว่าเป็น default เพราะ `CancelledError` สืบทอดจาก `BaseException` ไม่ใช่ `Exception` โดยตั้งใจ เพื่อไม่ให้ error handler ทั่วไปดักมันไป

**Caught by:** `ruff`'s `E722` สำหรับ bare `except:` และ `S110` สำหรับรูปแบบ `try`/`except`/`pass`:

```text
E722 Do not use bare `except`
S110 `try`-`except`-`pass` detected, consider logging the exception
```

สำหรับรูปแบบ async `except BaseException` `ruff`'s `BLE001` (blind-except) จับได้ตรง ๆ:

```text
BLE001 Do not catch blind exception: `BaseException`
```

`BLE001` **ไม่** ทำงานกับรูปแบบ bare `except:` / `except: pass` ข้างบน — อันนั้นถูกจับโดย `E722`/`S110` เท่านั้น ดู **[Exceptions](/python/th/typing-errors/exceptions/)**

### 7. `raise e` แทนที่จะเป็น bare `raise` เพิ่ม frame ที่ไม่จำเป็น — และโค้ด AI เขียนแบบนี้บ่อยมาก

```python
def a():
    b()

def b():
    raise ValueError("deep failure")

def reraise_bare():
    try:
        a()
    except ValueError:
        raise

def reraise_e():
    try:
        a()
    except ValueError as e:
        raise e
```

**อาการ — output จริง** นับ traceback frame ด้วย `traceback.extract_tb`:

```text
bare raise frames: 4
raise e frames: 5
```

ทั้งคู่ re-raise "exception เดียวกัน" แต่ `raise e` เพิ่ม frame มาอีกหนึ่ง — บรรทัด `raise e` เอง — เข้าไปใน traceback บน call stack ที่ลึก มันทำให้ traceback ยาวขึ้นและอ่านสับสนขึ้นเล็กน้อย โดยไม่ได้ประโยชน์อะไรเลย

**ทางแก้:** ใช้ bare `raise` เพื่อ re-raise exception แบบไม่เปลี่ยนแปลง

**Caught by:** `ruff`'s `TRY201` ตรง ๆ:

```text
TRY201 Use `raise` without specifying exception name
help: Remove exception name
```

```python
def withdraw(balance: int, amount: int) -> int:

print(withdraw(100, 30))
print(withdraw(100, 999))
```

**อาการ — output จริง รันปกติ:**

## Async & concurrency

### 9. Coroutine ที่สร้างโดยไม่มี `await` ไม่เคยรัน

```python
async def greet(name: str) -> None:
    await asyncio.sleep(0.01)
    print(f"hello, {name}")


async def main() -> None:
    greet("Ada")  # missing await -- creates a coroutine object, never runs it
    await asyncio.sleep(0.02)
    print("main done")
```

การเรียก `greet("Ada")` โดยไม่มี `await` ไม่รัน body ของ function เลย — มันสร้าง coroutine *object* แล้วทิ้งมันทันที `"hello, Ada"` ไม่เคยพิมพ์เลย

**อาการ — output จริง** (จับด้วยการครอบการเรียกด้วย `warnings.catch_warnings(record=True)` เพื่อให้ demo ยังรันได้ภายใต้ verifier ของคอร์สนี้ ที่เปลี่ยน `RuntimeWarning` ให้เป็น error):

```text
caught: RuntimeWarning: coroutine 'greet' was never awaited
main done
```

มีแค่ `"main done"` ที่พิมพ์ — greeting ไม่เคยเกิดขึ้นแบบเงียบ ๆ ถ้าไม่ครอบด้วย `catch_warnings` Python ยังรายงานสิ่งนี้ทันทีที่ coroutine object ที่ถูกทิ้งไว้ถูก garbage-collect:

```text
Exception ignored while finalizing coroutine <coroutine object greet at 0x...>:
RuntimeWarning: coroutine 'greet' was never awaited
```

**ทางแก้:** เพิ่ม `await greet("Ada")` ที่ขาดไป หรือถ้าการเรียกนั้นตั้งใจให้รันเบื้องหลังจริง ๆ ใช้ `asyncio.create_task(greet("Ada"))` แล้วเก็บ reference ของ task ไว้ (ดู pattern 10)

**Caught by:** ไม่มีอะไรแบบ static — ไม่มี linter ตัวไหนพิสูจน์ได้โดยทั่วไปว่าการเรียกที่คืน coroutine ขาด `await` มีแค่การรันโค้ดจริง (`python3.14 -X dev`) เท่านั้นที่เผย `RuntimeWarning` และเผยได้ก็ต่อเมื่อ coroutine ที่ถูกทิ้งไว้ถูก garbage-collect ระหว่างการรันจริง ๆ ดู **[asyncio basics](/python/th/async-concurrency/asyncio-basics/)**

### 10. Fire-and-forget `create_task` — task หายไปก่อนที่มันจะรันได้

```python
async def send_metric(name: str) -> None:
    await asyncio.sleep(0.2)
    print(f"metric sent: {name}")  # this line may never run


async def handle_request(n: int) -> str:
    asyncio.create_task(send_metric(f"request-{n}"))  # no reference kept anywhere
    return f"response-{n}"


async def main() -> None:
    results = [await handle_request(i) for i in range(3)]
    print(results)
    # main returns immediately -- nothing is waiting for the background tasks
```

**อาการ — output จริง:**

```text
['response-0', 'response-1', 'response-2']
```

ไม่มีบรรทัด `"metric sent: ..."` ทั้งสามบรรทัดพิมพ์ออกมาเลย `asyncio.run(main())` ปิด event loop ทันทีที่ `main` return ยกเลิกทุก task ที่ไม่มีใคร await อยู่ — แบบเงียบ ๆ ไม่มี error ไม่มี warning ในการรันนี้

```python
background_tasks: set[asyncio.Task] = set()

def spawn(coro) -> None:
    task = asyncio.create_task(coro)
    background_tasks.add(task)
    task.add_done_callback(background_tasks.discard)
```

### 11. `time.sleep` ข้างใน async code block event loop ทั้งหมด

```python
async def slow_task(n: int) -> None:

    print(f"task {n} done")


async def main() -> None:
    start = time.perf_counter()
    await asyncio.gather(slow_task(1), slow_task(2), slow_task(3))
    elapsed = time.perf_counter() - start
    print(f"elapsed: {elapsed:.2f}s (should be ~0.3s if truly concurrent)")
```

**อาการ — output จริง:**

```text
task 1 done
task 2 start
task 2 done
task 3 start
task 3 done
elapsed: 0.93s (should be ~0.3s if truly concurrent)
```

ทั้งสาม task รันเรียงกันทีละตัว ใช้เวลารวมประมาณ 3 เท่าของที่ควรจะเป็นถ้ามันซ้อนกันจริง ๆ — `asyncio.gather` ดูเหมือน concurrent ใน source แต่ถูก serialize เต็มรูปแบบตอน runtime การรันด้วย `-X dev` (ซึ่งเปิด asyncio debug mode ด้วย) ยัง log slow-callback warning สำหรับแต่ละ task ที่ถูก block:

### 12. Shared mutable state ถูก mutate คาบเกี่ยว `await` โดยไม่มี lock

```python
class Account:
    def __init__(self, balance: int) -> None:
        self.balance = balance

    async def withdraw(self, amount: int) -> bool:
        if amount > self.balance:
            return False
        await asyncio.sleep(0)  # simulates an awaited I/O call mid-operation
        self.balance -= amount  # another task can run between the check and this line
        return True


async def main() -> None:
    acct = Account(balance=100)
    results = await asyncio.gather(
        acct.withdraw(80),
        acct.withdraw(80),
    )
    print("withdraw results:", results)
    print("final balance:", acct.balance)
```

การเรียก `withdraw` ทั้งสองครั้งเช็ค `amount > self.balance` (`80 > 100` เป็น `False` ทั้งคู่) *ก่อน* ที่ทั้งคู่จะไปถึง `await` — event loop สามารถสลับระหว่างทั้งสองที่จุด `await` นั้นได้ และทั้งคู่ก็ดำเนินการลบ `80` ต่อ ทั้งที่ account มี `100` เท่านั้น

**อาการ — output จริง:**

```text
withdraw results: [True, True]
final balance: -60
```

การถอนทั้งสองครั้งรายงานว่าสำเร็จ และ balance ติดลบ — race แบบ time-of-check-to-time-of-use แบบคลาสสิก เกิดขึ้นได้จาก `await` ใด ๆ ระหว่างการเช็คกับการ mutate ไม่ใช่จาก OS-thread parallelism จริง

**ทางแก้:** ครอบทั้งลำดับ check-then-mutate ด้วย `asyncio.Lock`:

```python
def __init__(self, balance: int) -> None:
    self.balance = balance
    self._lock = asyncio.Lock()

async def withdraw(self, amount: int) -> bool:
    async with self._lock:
        if amount > self.balance:
            return False
        await asyncio.sleep(0)
        self.balance -= amount
        return True
```

**Caught by:** ไม่มี นี่คือ race condition จริง — การเกิดขึ้นของมันขึ้นอยู่กับลำดับการสลับที่ event loop เลือกใช้จริง ๆ และไม่มีเครื่องมือ static ตัวไหนพิสูจน์หรือหักล้างมันได้ ดู **[Tasks & gather](/python/th/async-concurrency/async-await/)**

### 14. `__eq__` ถูกนิยามโดยไม่มี `__hash__` ทำให้ instance กลายเป็น unhashable

```python
class Point:
    def __init__(self, x: int, y: int) -> None:
        self.x = x
        self.y = y

    def __eq__(self, other: object) -> bool:
        if not isinstance(other, Point):
            return NotImplemented
        return self.x == other.x and self.y == other.y


p = Point(1, 2)
print(p == Point(1, 2))
print({p})
```

การนิยาม `__eq__` บน class ทำให้ Python ตั้ง `__hash__` เป็น `None` อัตโนมัติ เว้นแต่คุณจะนิยาม `__hash__` เองด้วย — สอง object ที่เทียบเท่ากันต้อง hash เท่ากัน และ Python ไม่สามารถรับประกันสิ่งนั้นให้ class ที่มันไม่ได้ควบคุมการ hash ของ

**อาการ — output จริง:**

```text
True
Traceback (most recent call last):
  ...
TypeError: cannot use 'Point' as a set element (unhashable type: 'Point')
```

`p == Point(1, 2)` ทำงานได้ปกติ การใส่ `Point` ลงใน `set` (หรือใช้เป็น `dict` key) พังทันที

**ทางแก้:** นิยาม `__hash__` คู่กับ `__eq__` ถ้า instance จำเป็นต้อง hashable (และ immutable โดยพฤตินัย) หรือยอมรับว่า class นี้ตั้งใจให้ unhashable และเอกสารไว้:

```python
def __hash__(self) -> int:
    return hash((self.x, self.y))
```

**Caught by:** `ruff`'s `PLW1641` ตรง ๆ:

```text
PLW1641 Object does not implement `__hash__` method
```

### 15. Class attribute ที่ mutable ถูกแชร์ทุก instance

### 18. `list[Dog]` ถูกส่งไปในจุดที่คาดหวัง `list[Animal]` — generic invariance

```python
class Dog(Animal):

class Cat(Animal):

def add_a_cat(animals: list[Animal]) -> None:

dogs: list[Dog] = [Dog(), Dog()]
```

```text
  ...
TypeError: can't compare offset-naive and offset-aware datetimes
```

### 20. `open()` โดยไม่มี `with` และไม่มี `encoding=`

```python
def read_report(path: str) -> str:
    f = open(path)  # no `with`, no encoding= -- leaks the fd, platform-dependent decoding
    data = f.read()
    f.close()
    return data
```

สองปัญหาแยกกันในบรรทัดเดียว: ไม่มี `with` แปลว่า file descriptor ยังเปิดค้างอยู่ถ้า `f.read()` raise ก่อนที่ `f.close()` จะรัน ไม่มี `encoding=` แปลว่า text ถูก decode ด้วย locale encoding default ของ platform ซึ่งเป็น UTF-8 บน Linux/macOS ส่วนใหญ่ทุกวันนี้ แต่ **ไม่รับประกัน** — โค้ดเดียวกันเป๊ะสามารถ decode ต่างกันบนเครื่องอื่น

**อาการ — output จริง** (บนเครื่อง Unix นี้ ด้วย UTF-8 locale สิ่งนี้ round-trip สะอาดพอดี — อันตรายจริงมองเห็นได้เฉพาะข้าม platform เท่านั้น ซึ่ง environment นี้ไม่สามารถจำลองได้อย่างซื่อสัตย์):

```text
'héllo\n'
```

**ทางแก้:** ใช้ `with` เสมอ และส่ง `encoding=` อย่างชัดเจนเสมอ:

```python
def read_report(path: str) -> str:
    with open(path, encoding="utf-8") as f:
        return f.read()
```

### 21. `subprocess(..., shell=True)` กับ untrusted input คือ shell injection

```python
import subprocess

def list_files(directory: str) -> str:
    result = subprocess.run(f"ls {directory}", shell=True, capture_output=True, text=True)
    return result.stdout

print(list_files(". ; echo INJECTED"))
```

`shell=True` รัน string ทั้งหมดผ่าน `/bin/sh` ซึ่งตีความ `;`, `&&`, backtick และ `$()` — attacker (หรือแค่ input ที่ไม่เรียบร้อย) สามารถต่อคำสั่งอื่นเข้าไปได้

**อาการ — output จริง:** directory listing ตามด้วยบรรทัดที่ไม่เคยเป็นส่วนหนึ่งของชื่อไฟล์ใดเลย:

```text
... (directory listing) ...
INJECTED
```

`; echo INJECTED` ใน argument รันเป็นคำสั่ง shell ที่สองที่แยกออกมาต่างหากโดยสมบูรณ์

**ทางแก้:** ส่ง list ของ argument และห้ามตั้ง `shell=True` เลยสำหรับอะไรก็ตามที่สร้างจาก external input:

```python
def list_files(directory: str) -> str:
    result = subprocess.run(["ls", directory], capture_output=True, text=True)
    return result.stdout
```

**Caught by:** `ruff`'s `S602` (และ `bandit`'s `B602` บวก `B404` สำหรับการ import `subprocess` เลย) ตรง ๆ:

```text

```

### 22. `mock.patch` patch ผิดตำแหน่ง

```python
# weather_from_import.py
from requests import get

def get_temperature(city: str) -> float:
    response = get(f"https://api.example.com/weather/{city}")
    return response.json()["temp"]
```

```python
# test_weather_from_import_wrong.py
from unittest.mock import patch
import weather_from_import

@patch("requests.get")  # WRONG: weather_from_import already bound its own name `get`
def test_get_temperature(mock_get):
    mock_get.return_value.json.return_value = {"temp": 72.0}
    result = weather_from_import.get_temperature("bangkok")  # calls the REAL requests.get
    assert result == 72.0
```

`unittest.mock.patch("requests.get")` แทนที่ attribute `get` บน module `requests` แต่ `weather_from_import.py` ทำ `from requests import get` — นั่นสร้างชื่อ `get` *ของตัวเอง* แยกต่างหากข้างใน module `weather_from_import` ที่ผูกกับ function เดิมตอน import time การ patch `requests.get` ทีหลังไม่แตะ `weather_from_import.get` เลย

**อาการ — pytest output จริง:**

```text
requests.exceptions.ConnectionError: HTTPSConnectionPool(host='api.example.com', port=443): Max retries exceeded with url: /weather/bangkok (Caused by NameResolutionError("...Failed to resolve 'api.example.com'..."))
1 failed in 0.14s
```

mock มีผลเป็นศูนย์ — test เรียก network จริงไปยัง domain ที่ไม่มีอยู่จริง และ fail ด้วย DNS error ไม่ใช่ด้วยค่า mocked ใน CI environment ที่สภาพ network ต่างออกไป bug เดียวกันนี้สามารถทำให้ test **ผ่าน** แบบผิด ๆ ได้เช่นกัน ถ้า code path บังเอิญทนต่อ call จริงได้ — ดู **[Worked Review 4](/python/th/reading-python/worked-review-4/)** สำหรับ variant นั้น

**ทางแก้:** patch ชื่อ *ตามที่ถูก lookup จาก module ที่ถูกทดสอบ* เสมอ — `@patch("weather_from_import.get")` ไม่ใช่ `@patch("requests.get")` เพราะนั่นคือ attribute จริงที่โค้ดที่ถูกทดสอบจะเรียก

**Caught by:** ไม่มี ไม่มีเครื่องมือไหนตรวจว่า target string ของ `@patch` ตรงกับวิธีที่โค้ดที่ถูกทดสอบ import ชื่อนั้นมาจริง ๆ หรือเปล่า test สามารถ fail ดัง ๆ (แบบนี้) หรือผ่านแบบเงียบ ๆ ด้วยเหตุผลผิด ๆ ก็ได้ มีแค่คนที่อ่านทั้งสองไฟล์เทียบกันเท่านั้นที่จับได้ ดู **[pytest](/python/th/stdlib-testing-tooling/pytest/)**

### 23. `requirements.txt` ไม่ pin หรือติดตั้งด้วย `sudo pip`

```text

```

dependency ที่ไม่ pin (`requests` ไม่มี version) จะ resolve เป็น version ล่าสุดที่ compatible *ในวันที่ใครสักคนรัน `pip install`* — `requirements.txt` เดียวกันเป๊ะสามารถติดตั้งโค้ดที่ต่างกัน อาจมีช่องโหว่ ห่างกันแค่หนึ่งเดือน `sudo pip install ...` ติดตั้งเข้าไปใน system Python ที่ตัว operating system เองพึ่งพาอยู่ ซึ่งสามารถทำลาย OS tooling อื่นที่ไม่เกี่ยวข้องแบบเงียบ ๆ และต้องการสิทธิ์ root สำหรับสิ่งที่ควรเป็น operation ระดับ user หรือ project เท่านั้น

**อาการ — `pip-audit` output จริง** รันกับบรรทัดที่ pin ไว้ข้างบนพอดี:

```text

------- ------- --------------- -------------
urllib3 1.26.4  PYSEC-2021-108  1.26.5
```

การ pin จำเป็นต่อ reproducibility แต่ไม่พอในตัวมันเอง — การ pin สามารถ freeze version ที่ *มีช่องโหว่ที่รู้อยู่แล้ว* ไว้ตลอดไปได้เช่นกัน ซึ่งเป็นสิ่งที่ tooling audit ของ `pip-audit`/`uv` มีไว้จับอย่างต่อเนื่องพอดี

**Caught by:** เครื่องมือ `pip-audit`/`uv audit`-เทียบเท่าจับ version ที่ pin ไว้แล้วแต่มีช่องโหว่ได้ ตามที่แสดงข้างบน ไม่มีอะไร automated จับ requirement ที่ *ไม่ pin* เอง และไม่มีอะไร automated หยุด `sudo pip install` — ทั้งสองอย่างเป็นเรื่อง process discipline ไม่ใช่สิ่งที่ linter มองเห็นได้ ดู **[venv, pip & uv](/python/th/stdlib-testing-tooling/venv-pip/)**

### 24. `print()` แทนที่จะเป็น `logging` ในโค้ดที่เป็น library

```python
def process_batch(items: list[int]) -> list[int]:

            print(f"skipping invalid item: {item}")  # library code -- caller can't filter/redirect this

        results.append(item * 2)
    return results

```

```text

[2, 6]
```

```python
import logging

        results.append(item * 2)

```
